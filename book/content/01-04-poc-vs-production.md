## 학습 목표와 선수 개념

- PoC가 답해야 할 질문을 미리 정하고, 그 질문에 필요한 만큼만 만든다.
- PoC 코드가 운영에서 실패하는 전형적인 지점을 찾는다.
- 운영 전환 체크리스트로 남은 일을 고객과 합의한다.

선수 개념: 1.2·1.3절. 2–5장의 용어는 여기서 처음 보면 이름만 기억하고 넘어가도 된다.

## 현장 상황

2주 만에 만든 PoC 데모가 큰 호응을 얻었다. 임원이 "다음 달부터 전 지점에 쓰자"고 한다. 그런데 이 코드는 FDE 노트북에서 돌고, DB 주소와 API 토큰이 코드에 박혀 있으며, 외부 API가 느려지면 멈추고, 테스트도 로그도 없다. OpenAI FDE 공고는 PoC 프로토타입과 운영 배포 각각의 작업 범위와 계획을 쓰는 일을 FDE의 업무로 적는다. 둘은 다른 질문에 답하는 다른 산출물이다.

## 원리와 용어

- **PoC(Proof of Concept, 개념 증명)**: "이 방법이 이 고객의 데이터와 업무에서 통하는가?"라는 **질문 하나에 답하기 위한** 최소한의 구현. 성공 조건과 종료 시점을 정해 두고 시작한다. 답을 얻으면 버려도 되는 코드다.
- **파일럿**: 실제 사용자 일부가 실제 업무에 짧게 써 보는 단계. 1.3절의 수용 기준을 재는 곳이다.
- **운영 제품**: 고객이 매일 의존하는 시스템. 실패해도 피해가 제한되고, 문제를 알아차리고, 되돌릴 수 있고, FDE가 떠난 뒤에도 고객이 운영할 수 있어야 한다.

PoC가 일부러 생략하는 것과 운영에서 필요한 것:

| 영역 | PoC에서 흔한 상태 | 운영에서 필요한 것 | 이 책 |
|---|---|---|---|
| 실패 처리 | 성공 경로만 | 시간 제한, 재시도, 멱등성, 부분 실패 격리 | 2.4, 2.5 |
| 데이터 | 샘플 파일, 정제 수작업 | 정제 규칙 코드화, 품질 검사, 증분 적재 | 3.3, 3.4 |
| 보안 | 관리자 토큰 하나 | 최소 권한, 객체 수준 권한, 비밀값 분리 | 4.3, 5.5 |
| 개인정보 | 원본 덤프 사용 | 최소화, 가명화, 접근 통제 | 3.5 |
| 품질 | 데모 몇 건 | 테스트, 평가셋, 수용 기준 | 4.2, 6.4 |
| 배포 | 내 노트북 | 컨테이너, CI, 단계적 배포, 롤백 | 4.4 |
| 운영 | 문제가 나면 FDE에게 전화 | 로그·지표·경보, 런북, 장애 대응 | 5.1, 5.4, 7.3 |

## 예제: PoC 코드 한 함수의 운영 점검(분석 사례)

PoC의 배송 상태 조회 함수다(실행하지 않는 분석용 코드).

```python
def shipping_status(order_id):
    token = "sk_live_3f9..."                                   # (1)
    r = requests.get(f"https://carrier.example/track?no={order_id}&key={token}")  # (2)(3)
    return r.json()["status"]                                   # (4)
```

운영 관점의 점검:

1. **비밀값이 코드에 있다**: 저장소에 남고 이미지·로그로 퍼진다. 환경 변수나 비밀 저장소로 옮기고, 이미 커밋됐다면 폐기·재발급한다(4.3절).
2. **시간 제한이 없다**: 배송사 API가 응답하지 않으면 요청이 끝없이 기다리고 서버의 작업자가 고갈된다(2.4절).
3. **토큰이 URL 쿼리에 있다**: URL은 프록시·서버 로그에 그대로 남는다. 헤더로 보낸다(2.2절). 주문번호도 인코딩 없이 붙어 있다.
4. **응답을 검증하지 않는다**: 4xx·5xx나 HTML 오류 페이지면 `KeyError`나 JSON 오류로 호출한 화면 전체가 실패한다. 상태 코드를 확인하고, 실패 시 "확인 불가"를 표시해 상담원이 수작업으로 넘어갈 수 있게 한다(2.1절).

고친 모양의 뼈대:

```python
def shipping_status(order_id, settings, http):
    try:
        r = http.get(f"{settings.carrier_url}/track", params={"no": order_id},
                     headers={"Authorization": f"Bearer {settings.carrier_token.value}"}, timeout=3)
    except TimeoutError:
        log.warning("carrier timeout", extra={"order_id": order_id})
        return {"status": "unknown", "reason": "timeout"}
    if r.status != 200:
        log.warning("carrier error", extra={"order_id": order_id, "http_status": r.status})
        return {"status": "unknown", "reason": f"http {r.status}"}
    return {"status": parse_status(r.json())}  # parse_status는 허용 값만 통과시키고 테스트로 고정한다
```

같은 기능이지만 실패해도 화면이 멈추지 않고, 로그가 남고, 설정과 비밀값이 분리되어 테스트할 수 있다.

### 운영 전환 체크리스트(고객과 함께 채우는 표)

| 항목 | 상태 | 담당 | 완료 조건 |
|---|---|---|---|
| 수용 기준 충족(1.3) | 3/4 | FDE·운영팀장 | 긴급 누락 0건으로 2주 |
| 비밀값 분리·교체(4.3) | 진행 중 | FDE·고객 IT | 저장소 탐지 0건 |
| 권한 표 테스트(5.5) | 미시작 | FDE | 사용자×객체 표 전부 통과 |
| 경보와 런북(5.1, 7.3) | 미시작 | 고객 IT | 장애 모의 훈련 1회 |
| 롤백 절차(4.4) | 문서만 | 고객 IT | 스테이징에서 실제 롤백 1회 |

## 흔한 오류와 디버깅

- **질문 없는 PoC**: 무엇을 증명할지 정하지 않으면 "되긴 되네요"로 끝나고 다음 결정의 근거가 없다.
- **PoC 코드를 그대로 확장**: 데모용 지름길(하드코딩, 예외 무시)이 운영 장애가 된다. 전환 시점에 다시 설계할 부분을 명시한다.
- **데모 성공 = 운영 준비 완료로 보고**: 체크리스트의 남은 항목과 예상 기간을 함께 보고한다.
- **FDE에게만 있는 지식**: 실행 방법과 판단 기록이 FDE 머릿속에만 있으면 인수인계가 불가능하다(7.3절).

## 이해 확인

::quiz
고객이 "PoC에서 정확도 90%가 나왔으니 바로 전 지점에 배포하자"고 한다. 1.3절과 이 절의 내용으로 확인할 것 세 가지를 들어라.
::answer
(1) 그 90%가 어떤 데이터로 잰 것인지: 손으로 고른 데모 사례인지, 실제 분포를 반영한 평가셋인지(6.4절). (2) 합의한 수용 기준과 반대 지표(예: 긴급 누락, 오배정)를 파일럿에서 실제 사용자로 쟀는지. (3) 운영 전환 체크리스트: 비밀값 분리, 권한 검사, 시간 제한·실패 처리, 모니터링·롤백 절차가 준비됐는지. 전 지점 배포 대신 일부 지점 단계적 배포(4.4절)를 제안할 수 있다.
::end

::quiz
분석 사례의 원래 함수에서 배송사 API가 HTML 오류 페이지를 200으로 돌려준다면 어떤 일이 생기고, 고친 뼈대는 이를 어디서 막는가?
::answer
`r.json()`이 JSON 해석 오류로 예외를 던져 호출한 화면 전체가 실패한다. 고친 뼈대는 상태 코드만으로는 막지 못하므로, `parse_status`가 JSON 해석 실패와 허용되지 않은 값을 처리해 "확인 불가"를 돌려주도록 해야 한다. 상태 코드가 200이어도 내용이 틀릴 수 있다는 점은 5.1절의 "내용이 틀린 200도 오류"와 같은 원리다.
::end
