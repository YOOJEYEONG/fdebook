## 학습 목표와 선수 개념

- 인증·기능 수준 권한·객체 수준 권한의 차이를 구분한다.
- OWASP API Security Top 10의 API1(객체 수준 권한 검사 실패)을 재현하고 고친다.
- 자산·행위자·진입점·통제로 간단한 위협 모델을 쓴다.

선수 개념: 2.2절(401/403), 3.5절.

## 현장 상황

여러 고객사가 함께 쓰는 문의 관리 시스템을 붙이는 프로젝트다. 출시 직전 고객사 보안팀이 테스트하다가, 로그인한 상태에서 URL의 문의 번호를 102로 바꾸자 **다른 회사의 문의**가 보였다. 화면에서는 자기 회사 문의만 보였기 때문에 아무도 몰랐다. Palantir FDE 공고는 접근 통제와 권한을 개발 전 과정의 요건으로, Anthropic Staff FDE 공고는 보안·조달 관문을 미리 예상하는 것을 FDE의 일로 적는다.

## 원리와 용어

- **인증**: 누구인가(2.2절의 401).
- **기능 수준 권한**: 이 사람이 이 **기능**을 쓸 수 있는가. viewer는 문의를 닫을 수 없다. OWASP API5:2023 Broken Function Level Authorization.
- **객체 수준 권한**: 이 사람이 이 **특정 객체**에 접근할 수 있는가. 문의 102는 다른 회사의 것이다. OWASP API1:2023 Broken Object Level Authorization. OWASP는 사용자가 넘긴 ID로 데이터를 읽는 모든 함수에서 그 객체에 대한 권한을 검사하라고 설명한다. API 위험 목록의 1번이다.
- **테넌트**: 시스템을 함께 쓰는 고객 단위. 다중 테넌트 시스템에서 가장 중요한 경계다.

화면에서 버튼을 숨기는 것은 권한 검사가 아니다. 공격자는 화면을 거치지 않고 API를 직접 부른다. 권한 검사는 **서버에서, 객체를 읽을 때마다** 한다. 가장 안전한 방법은 질의 자체에 테넌트 조건을 넣는 것이다(`WHERE id = ? AND tenant_id = ?`). 그러면 검사를 빠뜨릴 여지가 줄어든다.

**위협 모델**: 무엇을 지키고(자산), 누가 공격할 수 있으며(행위자), 어디로 들어오는지(진입점), 무엇으로 막는지(통제)를 표로 정리한다. 거창한 방법론 이전에, 고객 보안 검토에서 받을 질문에 미리 답하는 도구다.

| 자산 | 행위자 | 진입점 | 통제 |
|---|---|---|---|
| 고객사 문의 내용 | 다른 테넌트의 사용자 | `GET /tickets/{id}` | 객체마다 테넌트 확인, 질의에 테넌트 조건 |
| 문의 상태 변경 | 권한 낮은 내부 사용자 | `POST /tickets/{id}/close` | 역할별 기능 권한, 감사 로그 |
| 웹훅 수신 | 외부 위조자 | `POST /webhooks` | HMAC 서명, 타임스탬프, 이벤트 ID(2.6절) |
| API 토큰 | 로그 열람자 | 로그·오류 메시지 | 헤더 가림, 비밀 저장소(4.3절) |

## 흔한 오류와 디버깅

- **목록에서는 거르고 상세에서는 안 거름**: 목록 API는 테넌트로 거르지만 상세 API는 ID만 본다. 엔드포인트마다 검사한다.
- **순차 ID**: 1, 2, 3… 같은 ID는 추측하기 쉽다. 추측하기 어려운 ID는 보조 수단일 뿐이고, 권한 검사를 대신하지 못한다.
- **클라이언트가 보낸 테넌트 ID를 신뢰**: 요청 본문의 `tenant_id`가 아니라 인증된 사용자 정보에서 테넌트를 얻는다.
- **관리자 기능 노출**: 내부용 엔드포인트가 같은 서버에 인증 없이 열려 있다. 목록(인벤토리)을 만들고 점검한다(OWASP API9:2023).

## 이해 확인

::quiz
`GET /tickets?tenant_id=가나물류` 목록 API가 있다. 요청한 사용자가 다라상사 소속인데 `tenant_id=가나물류`를 넣으면 어떻게 되어야 하며, 서버는 테넌트 값을 어디서 가져와야 하는가?
::answer
다른 회사의 목록이 나와서는 안 된다. 서버는 쿼리 매개변수가 아니라 인증된 사용자 정보(토큰에 연결된 계정)에서 테넌트를 가져와 질의 조건으로 써야 한다. 매개변수는 무시하거나, 사용자 테넌트와 다르면 거부한다.
::end

예: 행위자 — 업무상 필요 이상으로 조회하는 내부 사용자. 진입점 — 상담 화면과 고객 상세 API. 통제 — 기본은 마스킹(3.5절), 본인 확인 등 필요할 때만 전체 표시, 전체 표시할 때마다 감사 로그 기록, 역할별 권한. 답은 여러 가지일 수 있으며 중요한 것은 자산마다 구체적인 통제가 있는지다.
::end
