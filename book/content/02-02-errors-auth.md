## 학습 목표와 선수 개념

- 4xx 상태 코드 가운데 400, 401, 403, 404, 409, 422가 각각 무엇을 알려 주는지 구분한다.
- 오류 응답 본문을 RFC 9457의 problem details 형식으로 설계한다.
- **인증**(누구인가)과 **인가·권한**(무엇을 해도 되는가)을 나누어 검사한다.

선수 개념: 2.1절의 요청·응답 구조.

## 현장 상황

고객사의 상담원 화면에서 "티켓 만들기" 버튼이 가끔 실패한다. 화면에는 "오류가 발생했습니다"만 보인다. 로그를 열어 보니 실패 응답이 모두 403이었다. 상담원 계정 일부에 쓰기 권한이 빠져 있었던 것이다. 상태 코드와 오류 본문이 정확했기에 원인을 몇 분 만에 찾았다. 반대로 모든 오류를 500이나 "error": "fail"로 돌려주는 API였다면 같은 문제를 찾는 데 며칠이 걸렸을 것이다.

## 원리와 용어

### 자주 만나는 4xx

| 코드 | 의미 | 클라이언트가 할 일 |
|---|---|---|
| 400 Bad Request | 요청 형식 자체가 잘못됨(깨진 JSON 등) | 요청을 고친다 |
| 401 Unauthorized | 인증 정보가 없거나 유효하지 않음 | 토큰을 새로 받는다 |
| 403 Forbidden | 누구인지는 알지만 이 일을 할 권한이 없음 | 권한을 요청한다. 같은 토큰으로 재시도해도 소용없다 |
| 404 Not Found | 대상이 없음(또는 존재를 숨김) | 경로·ID를 확인한다 |
| 409 Conflict | 현재 상태와 충돌(이미 처리 중 등) | 상태를 다시 읽고 판단한다 |
| 422 Unprocessable Content | 형식은 맞지만 내용이 규칙 위반 | 입력값을 고친다 |

401의 이름이 "Unauthorized"라서 헷갈리지만 의미는 **인증 실패**다. RFC 6750은 Bearer 토큰이 유효하지 않으면 401과 `WWW-Authenticate` 헤더에 `error="invalid_token"`을, 토큰에 필요한 권한 범위(scope)가 없으면 403과 `insufficient_scope`를 보내도록 권한다.

### Bearer 토큰

`Authorization: Bearer <토큰>` 헤더로 보내는 토큰이다. RFC 6750의 정의대로 **가진 사람이면 누구나** 쓸 수 있으므로 유출되면 그대로 악용된다. 그래서 HTTPS로만 보내고, 로그·URL·에러 메시지에 남기지 않으며, 짧은 유효 기간과 필요한 최소 권한 범위를 준다.

### 오류 본문: problem details

RFC 9457은 HTTP API 오류를 JSON으로 전달하는 공통 형식을 정한다. 미디어 타입은 `application/problem+json`이고 멤버는 다음과 같다.

- `type`: 문제 종류를 가리키는 URI. 없으면 `about:blank`.
- `title`: 문제 종류의 짧은 요약. 같은 종류면 매번 같다.
- `status`: 상태 코드(참고용, 실제 HTTP 상태와 같아야 한다).
- `detail`: 이번 발생에 대한 사람이 읽을 설명.
- `instance`: 이번 발생을 가리키는 URI(선택).

형식을 통일하면 클라이언트가 오류 처리 코드 하나로 모든 엔드포인트를 다룰 수 있고, 로그 검색도 쉬워진다.

## 흔한 오류와 디버깅

- **401과 403을 섞어 씀**: 클라이언트가 403을 받고 토큰 갱신을 반복하거나, 401을 받고 권한 요청 화면을 띄운다. 의미대로 나눈다.
- **모든 오류에 200과 `{"ok": false}`**: 모니터링이 오류율을 0으로 본다. 5.1절의 지표가 의미를 잃는다.
- **오류 본문에 내부 정보 노출**: 스택 트레이스, SQL, 다른 고객의 ID를 `detail`에 넣지 않는다. 내부 정보는 서버 로그에 요청 ID와 함께 남기고 응답에는 요청 ID만 준다.
- **토큰을 로그에 기록**: 요청 헤더 전체를 로그에 남기면 토큰이 함께 기록된다. `Authorization` 같은 헤더는 기록 전에 가린다.
- **본문을 읽지 않고 거절**: 이 예제의 첫 판은 인증 실패 시 요청 본문을 읽지 않고 401을 보냈다. 여러 번 실행하자 가끔 클라이언트가 `ConnectionResetError`로 응답을 읽지 못했다. 서버가 읽지 않은 데이터를 남긴 채 연결을 닫으면 운영체제가 연결을 재설정할 수 있기 때문이다. 거절하더라도 본문을 끝까지 읽거나(크기 상한을 두고) `Connection: close`를 명시한다. "가끔만" 나는 오류는 이렇게 반복 실행으로 재현한다(5.2절).
- **존재 노출**: 권한 없는 사용자에게 "있지만 볼 수 없음"(403)과 "없음"(404)을 다르게 답하면 다른 고객의 자원이 있는지 알려 주는 셈이다. 민감한 자원은 둘 다 404로 답하기도 한다(5.5절).

## 이해 확인

::quiz
읽기 권한만 있는 토큰으로 `DELETE /tickets/7`을 보냈다. RFC 6750의 권고에 맞는 상태 코드와 `WWW-Authenticate`의 `error` 값은?
::answer
403과 `insufficient_scope`. 토큰은 유효하므로 인증 실패(401, `invalid_token`)가 아니라 권한 범위 부족이다.
::end

::quiz
`{"subject": 123}`처럼 JSON 문법은 맞지만 `subject`가 문자열이 아닌 요청에 400과 422 중 무엇이 더 맞는가? 왜 팀 안에서 한쪽으로 정해 두어야 하는가?
::answer
본문을 JSON으로 해석할 수 있고 내용이 규칙에 어긋나므로 422가 의미상 더 정확하다. 다만 400을 쓰는 API도 흔하다. 중요한 것은 일관성이다. 클라이언트가 같은 종류의 실수에 늘 같은 코드를 받아야 오류 처리와 모니터링을 한 가지 규칙으로 만들 수 있다. 결정은 API 문서와 4.1절의 인터페이스 계약에 적는다.
::end

::quiz
고객이 "로그인한 사용자인데도 가끔 401이 난다"고 한다. 가능한 원인 두 가지와 확인 방법은?
::answer
(1) 토큰 만료: 응답의 `WWW-Authenticate`에 `invalid_token`이 있는지, 실패 시각과 토큰 발급 시각의 차이가 유효 기간과 맞는지 본다. (2) 헤더 누락: 프록시나 리다이렉트를 거치며 `Authorization` 헤더가 빠지는 경우가 있다. 서버 로그에서 실패 요청에 헤더가 도착했는지(값이 아니라 존재 여부만) 확인한다.
::end
