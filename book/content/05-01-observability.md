## 학습 목표와 선수 개념

- 로그·메트릭·트레이스가 각각 어떤 질문에 답하는지 구분한다.
- 한 줄 JSON 구조화 로그와 요청 ID를 쓴다.
- 네 가지 황금 신호(지연·트래픽·오류·포화)로 서비스 상태를 요약한다.

선수 개념: 2장(HTTP 상태 코드), 4.1절.

## 현장 상황

고객이 "문의 등록이 가끔 느리고 가끔 실패한다"고 한다. 서버 로그는 `print("error!")` 몇 줄뿐이고, 어떤 요청이 언제 왜 실패했는지 알 수 없다. 운영 중인 시스템을 고객에게 넘기려면(Anthropic Staff FDE 공고의 "고객이 운영할 수 있는 시스템") 고객의 운영팀이 이런 질문에 스스로 답할 수 있는 신호가 시스템 안에 있어야 한다.

## 원리와 용어

OpenTelemetry는 관측 신호를 다음처럼 정의한다.

- **로그(logs)**: "사건의 기록". 요청 하나, 오류 하나의 자세한 맥락.
- **메트릭(metrics)**: "실행 중 측정값". 요청 수, 오류 수, 지연 분포처럼 집계된 숫자. 싸고 빠르게 추세와 경보를 만든다.
- **트레이스(traces)**: "요청이 애플리케이션을 지나는 경로". 요청 하나가 거친 단계(**span**)들의 부모-자식 관계와 소요 시간. 어느 단계가 느린지 보여 준다.

세 신호를 잇는 열쇠는 **요청 ID**(트레이스 ID)다. 경보(메트릭) → 해당 시간대 오류 로그 → 로그의 요청 ID → 그 요청의 트레이스 순으로 좁혀 간다.

**구조화 로그**: 문장 대신 키-값(JSON) 한 줄로 남긴다. `level`, `request_id`, `route`, `status`, `duration_ms`처럼 정해진 필드가 있어야 "502인 POST만" 같은 검색이 된다. 개인정보와 비밀값은 필드에서 뺀다(3.5, 4.3절).

**메트릭 라벨의 카디널리티**: 메트릭에 붙이는 라벨은 값의 종류가 적어야 한다(경로 템플릿 `/tickets/{id}`, 상태 분류 `5xx`). 사용자 ID나 실제 경로(`/tickets/9381`)를 라벨로 쓰면 시계열이 폭증한다. 개별 값은 로그와 트레이스의 몫이다.

Google SRE Book은 사용자 대면 시스템이라면 최소한 **네 가지 황금 신호**를 보라고 권한다.

- **지연(latency)**: 요청 처리 시간. 성공과 실패의 지연을 나누어 본다. 느린 실패는 빠른 실패보다 나쁘다.
- **트래픽(traffic)**: 요청량(초당 요청 수 등).
- **오류(errors)**: 실패 비율. 명시적 실패(5xx)뿐 아니라 내용이 틀린 200, 약속한 시간을 넘긴 응답도 포함할 수 있다.
- **포화(saturation)**: 가장 부족한 자원이 얼마나 찼는가(연결 풀, CPU, 큐 길이).

경보는 원인보다 **증상**(사용자가 겪는 오류율·지연)에 건다. 원인 경보(CPU 80%)는 사용자 영향과 무관하게 울리기 쉽다.

해설:

- 로그는 요청마다 한 줄이다. 502 요청에는 `error` 필드로 원인을 적었다. 사람이 읽기는 조금 불편해도 도구로 거르고 집계하기 좋다.
- 메트릭은 개별 요청이 아니라 `(경로, 상태 분류)`별 수와 지연 범위다. 5xx 오류율 16.7%가 경보의 근거가 된다.
- 트레이스는 오류 로그에서 찾은 `req-04`의 단계별 시간이다. 3020ms 중 3000ms가 배송사 API 호출임이 한눈에 보인다. "DB가 느리다"는 추측을 데이터로 기각한다.
- 이 예제는 개념을 보이려고 직접 만들었다. 실제로는 OpenTelemetry SDK 같은 표준 도구로 계측하고, 신호를 수집·저장·검색하는 시스템으로 보낸다.

## 흔한 오류와 디버깅

- **요청 ID가 끊김**: 서비스 사이를 지날 때 ID를 헤더로 넘기지 않으면 트레이스가 끊긴다. 들어온 ID를 이어받고, 없을 때만 새로 만든다(W3C Trace Context의 `traceparent` 헤더가 표준이다).
- **평균만 봄**: 평균 지연은 꼬리를 숨긴다(5.3절). 백분위수를 본다.
- **로그 과다**: 모든 요청의 본문을 남기면 비용이 커지고 개인정보가 샌다. 필드를 정하고 수준(`info`/`error`)을 구분한다.
- **시간대 혼합**: 서버마다 로그 시각의 시간대가 다르면 사건 순서를 잘못 읽는다. UTC로 남기고 표시할 때 바꾼다(5.2절).

## 이해 확인

::quiz
메트릭 라벨에 `user_id`를 추가하자는 제안이 나왔다. 사용자가 10만 명이다. 무엇이 문제이며, "특정 사용자의 오류"는 어떻게 조사하는가?
::answer
라벨 값마다 별도 시계열이 생기므로 경로·상태 조합 × 10만 개의 시계열이 만들어져 저장·질의 비용이 폭증한다(높은 카디널리티). 특정 사용자의 문제는 로그나 트레이스에서 사용자 식별자(가명화한 값)로 검색해 조사한다. 메트릭은 전체 추세와 경보에 쓴다.
::end

::quiz
CPU 사용률 80% 초과 경보와 "5분간 5xx 비율 2% 초과" 경보 중 고객 영향과 더 잘 맞는 것은 무엇이며 왜인가?
::answer
5xx 비율 경보다. 사용자가 실제로 겪는 증상을 직접 측정한다. CPU 80%는 사용자 영향 없이도 자주 생기고(배치 작업 등), 반대로 CPU가 낮아도 외부 API 장애로 사용자는 실패를 겪을 수 있다. CPU 같은 원인 지표는 대시보드에서 진단용으로 본다.
::end
