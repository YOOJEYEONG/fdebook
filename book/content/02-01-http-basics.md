## 학습 목표와 선수 개념

이 절을 마치면 다음을 할 수 있다.

- HTTP 요청과 응답을 이루는 네 부분(시작 줄, 헤더, 빈 줄, 본문)을 구분한다.
- 메서드·경로·상태 코드·`Content-Type`을 보고 메시지가 무엇을 뜻하는지 읽는다.
- Python 표준 라이브러리만으로 JSON API를 호출하고 오류 응답을 처리한다.

선수 개념: 함수와 딕셔너리, 터미널에서 Python 파일 실행하기. 네트워크 지식은 없어도 된다.

## 현장 상황

물류 고객사가 "상담 시스템에서 티켓을 못 가져온다"고 연락했다. 고객의 개발자는 "API가 고장 났다"고 하고, 상담 시스템 공급사는 "우리 쪽은 정상"이라고 한다. 이때 FDE가 가장 먼저 할 일은 누구 말이 맞는지 판단하는 것이 아니라 **실제로 오간 요청과 응답을 보는 것**이다. 요청이 어디로 갔는지, 어떤 상태 코드가 돌아왔는지, 본문에 무엇이 있었는지를 보면 논쟁 대부분이 사실 확인으로 바뀐다.

## 원리와 용어

**HTTP**는 클라이언트(요청하는 쪽)와 서버(응답하는 쪽)가 텍스트 형식의 메시지를 주고받는 규칙이다. 의미는 표준 문서 RFC 9110이 정한다. 요청 하나는 다음처럼 생겼다.

```http
GET /tickets/1 HTTP/1.1
Host: api.example.com
Accept: application/json

```

- **시작 줄**: 메서드(`GET`), 대상 경로(`/tickets/1`), 프로토콜 버전.
- **헤더**: `이름: 값` 형식의 부가 정보. `Accept`는 "JSON으로 달라"는 뜻이다.
- **빈 줄**: 헤더가 끝났다는 표시.
- **본문**: 보낼 데이터. `GET`에는 보통 없다.

응답도 같은 구조다. 시작 줄에 **상태 코드**가 들어간다.

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 64

{"id": "1", "subject": "배송 지연 문의", "status": "open"}
```

**메서드**는 요청의 의도다. `GET`은 읽기, `POST`는 새로 만들거나 처리를 맡기기, `PUT`은 대상 전체를 이 값으로 바꾸기, `PATCH`는 일부 바꾸기, `DELETE`는 지우기다. RFC 9110은 `GET`·`HEAD`·`OPTIONS`·`TRACE`를 **안전한(safe)** 메서드, 즉 서버 상태를 바꾸려는 의도가 없는 메서드로 정의한다. 이 구분은 2.4절의 재시도에서 다시 중요해진다.

**상태 코드**는 세 자리 숫자이고 첫 자리가 분류다. 1xx 정보, 2xx 성공, 3xx 다른 곳으로 이동, 4xx 클라이언트 쪽 문제, 5xx 서버 쪽 문제. 위 현장 상황에서 404가 왔다면 "요청한 대상이 없다", 500이 왔다면 "서버가 처리 중 실패했다"이므로 다음에 확인할 곳이 달라진다.

**JSON**은 객체(`{}`), 배열(`[]`), 문자열, 숫자, `true`/`false`, `null`로 데이터를 표현하는 텍스트 형식이다. 응답의 `Content-Type: application/json`이 본문을 JSON으로 읽으라고 알려 준다. 한국어가 섞이면 문자 인코딩(대개 UTF-8)을 맞춰야 글자가 깨지지 않는다.

읽는 법:

- 서버는 경로에서 티켓 번호를 꺼내 있으면 200과 티켓을, 없으면 404와 오류 객체를 JSON으로 보낸다.
- `ensure_ascii=False`와 `charset=utf-8`이 한국어를 그대로 보내고 읽게 한다.
- `urllib`는 4xx·5xx 응답을 `HTTPError` 예외로 던진다. 예외 안에도 상태 코드와 본문이 있으므로 버리지 말고 읽어야 원인을 알 수 있다.
- `timeout=5`는 서버가 응답하지 않을 때 영원히 기다리지 않게 한다. 2.4절에서 자세히 다룬다.

## 흔한 오류와 디버깅

- **본문이 JSON이 아닌데 JSON으로 읽음**: 프록시나 로드밸런서가 HTML 오류 페이지를 돌려주면 `json.loads`가 실패한다. 먼저 상태 코드와 `Content-Type`을 확인하고 본문 앞부분을 로그에 남긴다.
- **한국어가 깨짐**: 보내는 쪽과 읽는 쪽의 인코딩이 다르다. `Content-Type`의 `charset`과 실제 바이트 인코딩을 맞춘다.
- **4xx를 "API 고장"으로 보고**: 4xx는 요청 쪽 문제를 뜻한다. 경로, 쿼리, 헤더, 인증 정보를 먼저 점검한다.
- **오류 본문을 버림**: 많은 API가 오류 원인을 본문에 적는다. 예외 처리에서 상태 코드와 본문을 함께 기록한다.

`curl -i` 명령은 응답의 시작 줄과 헤더를 함께 보여 주므로, 고객과 같은 화면을 보며 대화할 때 유용하다.

## 이해 확인

::quiz
고객 개발자가 "`GET /orders?status=shipped` 호출이 계속 실패한다"며 응답이 `HTTP/1.1 404 Not Found`라고 알려 왔다. 가장 먼저 확인할 것 두 가지는 무엇인가?
::answer
404는 서버가 요청한 대상을 찾지 못했다는 뜻이므로 요청 쪽을 먼저 본다. (1) 경로가 API 문서와 정확히 같은지(예: `/v1/orders`처럼 버전 접두사가 빠지지 않았는지, 호스트가 개발·운영 중 어디인지). (2) 본문에 서버가 적은 오류 설명이 있는지. 서버 장애를 의심하는 것은 5xx일 때다.
::end

::quiz
예제의 서버가 `Content-Type` 헤더를 `text/plain`으로 보낸다면 클라이언트 코드는 여전히 동작하는가? 동작한다면 무엇이 문제인가?
::answer
예제 클라이언트는 헤더를 확인하지 않고 본문을 바로 `json.loads`로 읽으므로 동작은 한다. 하지만 헤더가 본문 형식을 잘못 알리면 다른 클라이언트(브라우저, 자동 생성 SDK, 프록시)가 본문을 JSON으로 다루지 않을 수 있다. 계약대로 `application/json`을 보내고, 클라이언트도 `Content-Type`을 확인한 뒤 해석하는 편이 안전하다.
::end

::quiz
다음 중 RFC 9110에서 안전한(safe) 메서드가 아닌 것은? `GET`, `HEAD`, `POST`, `OPTIONS`
::answer
`POST`. 안전한 메서드는 서버 상태를 바꾸려는 의도가 없는 메서드이고, RFC 9110은 `GET`·`HEAD`·`OPTIONS`·`TRACE`를 꼽는다.
::end
