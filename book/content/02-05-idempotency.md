## 학습 목표와 선수 개념

- 멱등성의 정의와 POST가 멱등이 아닌 이유를 설명한다.
- `Idempotency-Key` 헤더를 받는 서버의 처리 규칙(재전송, 본문 불일치, 키 누락)을 구현한다.
- 키의 저장 위치와 동시 요청 문제를 판단한다.

선수 개념: 2.4절의 재시도와 멱등 메서드.

## 현장 상황

고객사의 주문 화면에서 "결제" 버튼을 누르면 결제 대행사 API를 호출한다. 모바일 네트워크가 끊기면 앱은 응답을 받지 못하고, 사용자는 버튼을 한 번 더 누른다. 월말 정산에서 같은 주문이 두 번 결제된 건이 발견됐다. 서버는 첫 요청을 정상 처리했지만 응답이 사용자에게 도착하지 못했던 것이다.

## 원리와 용어

**멱등성**: 같은 요청을 여러 번 보내도 서버에 남는 의도한 효과가 한 번 보낸 것과 같은 성질이다(RFC 9110 9.2.2). 클라이언트는 응답을 받지 못했을 때 "요청이 처리됐는지"를 알 수 없다. 서버가 처리하고 응답만 잃었을 수도, 아예 도착하지 않았을 수도 있다. 멱등이면 고민 없이 다시 보내면 된다.

**멱등성 키**: 클라이언트가 "한 번의 의도"마다 고유한 값(예: UUID)을 만들어 `Idempotency-Key` 헤더에 담는다. 서버는 키별로 첫 처리 결과를 저장해 두고, 같은 키가 다시 오면 처리하지 않고 저장한 결과를 돌려준다. 이렇게 하면 POST도 안전하게 재시도할 수 있다.

IETF의 `draft-ietf-httpapi-idempotency-key-header`(2026년 10월 갱신된 08판, 아직 표준 RFC가 아닌 초안)는 다음 규칙을 제안한다.

- 같은 키·같은 본문이 처리 완료 뒤 다시 오면 처리 완료와 일관된 응답을 준다.
- 같은 키가 **다른 본문**으로 오면 키를 잘못 재사용한 것이므로 422로 거절한다.
- 같은 키의 첫 요청이 **아직 처리 중**인데 또 오면 409로 충돌을 알린다.
- 키가 필요한 엔드포인트에 키가 없으면 400을 준다.
- 키를 얼마나 보관할지(만료)는 API 문서에 밝힌다.

키를 만드는 쪽은 **클라이언트**라는 점이 중요하다. 서버가 요청을 받은 뒤 만든 값은 응답을 잃으면 클라이언트가 알 수 없으므로 재전송에 쓸 수 없다.

## 예제: 결제 요청 네 번

::example ch2/idempotency.py

해설:

- 첫 요청은 결제를 만들고 `(본문 지문, 상태, 응답)`을 키와 함께 저장한다.
- 같은 키·같은 본문의 재전송은 결제를 새로 만들지 않고 `P-1`을 그대로 돌려준다. 클라이언트 입장에서는 첫 응답을 다시 받은 것과 같다.
- 같은 키로 금액이 다른 본문이 오면 422다. 본문 지문(SHA-256)을 비교해 알아낸다.
- 키 확인과 기록을 잠금(`lock`) 안에서 한 번에 한다. 그렇지 않으면 같은 키의 두 요청이 동시에 "처음 본 키"로 판단해 둘 다 결제할 수 있다. 여러 서버가 있으면 프로세스 안 잠금으로는 부족하므로 DB의 고유 제약(3.2절)이나 원자적 연산을 쓴다.
- 예제는 메모리에 저장하므로 서버가 재시작하면 기억을 잃는다. 실제로는 결제 기록과 키 기록을 **같은 트랜잭션**으로 DB에 남겨야 둘 중 하나만 저장되는 일이 없다.

## 흔한 오류와 디버깅

- **버튼을 누를 때마다 새 키 생성**: 재전송이 아니라 새 의도로 취급되어 중복이 그대로 생긴다. 키는 "결제 시도 화면을 열 때" 같은 의도 단위로 만들고 재시도에는 같은 키를 쓴다.
- **오류 응답도 저장할지 결정하지 않음**: 서버 내부 오류(5xx)까지 저장하면 일시적 장애가 영원히 재현된다. 어떤 결과를 저장할지 정책을 정한다.
- **키 만료가 재시도 기간보다 짧음**: 클라이언트가 하루 동안 재시도하는데 키를 한 시간만 보관하면 보호가 사라진다.
- **처리와 키 저장이 따로 커밋됨**: 처리 후 키 저장 전에 서버가 죽으면 다음 재전송이 다시 처리한다.

## 이해 확인

::quiz
클라이언트가 결제 버튼을 누를 때마다 `uuid4()`로 새 키를 만들어 보낸다. 사용자가 응답을 못 받고 버튼을 두 번 누르면 어떻게 되는가? 어떻게 고치는가?
::answer
두 요청의 키가 달라 서버는 서로 다른 결제로 보고 둘 다 처리한다. 키를 "주문 하나에 대한 결제 의도"마다 한 번 만들어(예: 주문 생성 시) 저장해 두고, 같은 주문의 재시도에는 그 키를 계속 쓴다.
::end

::quiz
예제의 `lock`을 지우고, 같은 키의 요청 두 개가 동시에 도착했다고 하자. 최악의 경우 무슨 일이 생기며 운영 환경(서버 여러 대)에서는 무엇으로 막는가?
::answer
두 요청이 모두 `key in seen`을 거짓으로 보고 각자 결제를 만든다(중복 결제). 서버가 여러 대면 프로세스 잠금은 효과가 없으므로, DB에 키를 고유 제약이 있는 열로 저장하고 "키 삽입에 성공한 요청만 처리"하게 하거나, 키를 먼저 "처리 중" 상태로 원자적으로 기록하고 두 번째 요청에는 409를 돌려준다.
::end
