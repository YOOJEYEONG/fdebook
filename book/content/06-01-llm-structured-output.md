## 학습 목표와 선수 개념

- LLM 호출의 입력(메시지, 시스템 지시, 최대 출력 길이)과 출력(본문, 종료 이유, 사용량)을 읽는다.
- 모델 출력을 프로그램이 쓰기 전에 스키마로 검증하고, 실패를 재시도·사람 검토로 나누어 처리한다.
- 구조화 출력 기능이 보장하는 것과 보장하지 않는 것을 구분한다.

선수 개념: JSON(2.1절), 인터페이스 계약(4.1절). JSON Schema는 "필드 이름·타입·허용 값을 적은 JSON 문서" 정도로 이해하면 충분하다.

## 현장 상황

고객사가 하루 수천 건의 상담 문의를 LLM으로 분류해 담당 팀에 자동 배정하려 한다. 시연에서는 잘 됐다. 운영 첫날, 모델이 가끔 JSON 앞에 "분류 결과입니다:"라는 문장을 붙이자 파서가 예외를 던졌고, 배정 프로그램이 멈춰 문의 수백 건이 쌓였다. OpenAI FDE 공고는 "모델 동작이 제품 경험에 어떤 영향을 주는지 이해"를 요구한다. 모델 출력은 다른 시스템의 입력이 되는 순간 **신뢰할 수 없는 외부 입력**이다.

이 장(6장)은 일반 FDE 역량(1–5장) 위에 얹는 **AI FDE 추가 역량**이다. 자료 조사(`docs/book-v2-source-audit.md`)에서 본 AI FDE 공고들(Databricks AI FDE, Palantir FD AI Engineer, OpenAI·Anthropic·Cohere FDE)은 모두 평가(evaluation)를 요구했다. 그래서 이 장은 "모델을 부르는 법"보다 "모델이 낸 결과를 검증하고 품질을 숫자로 증명하는 법"에 무게를 둔다.

## 원리와 용어

**LLM 호출의 모양**: 대부분의 LLM API는 메시지 목록(사용자·어시스턴트의 차례)과 시스템 지시를 입력으로 받고, 생성한 내용과 함께 **종료 이유**(`stop_reason`)와 **토큰 사용량**을 돌려준다. 토큰은 모델이 텍스트를 나누는 단위로, 비용과 길이 한도의 기준이다(6.6절). 같은 입력에도 출력이 달라질 수 있다(확률적 생성). 따라서 "한 번 해 봤더니 됐다"는 증거가 되지 않는다.

**종료 이유를 먼저 본다**: 정상 종료가 아니면 내용이 잘렸거나(`max_tokens`) 모델이 거절했을(`refusal`) 수 있다. Claude 문서는 구조화 출력을 쓰더라도 이 두 경우에는 출력이 스키마와 맞지 않을 수 있다고 명시한다.

**구조화 출력(structured outputs)**: 요청에 JSON Schema를 넘기면 모델의 출력을 그 스키마에 맞게 제약하는 기능이다. Claude API는 `output_config.format`에 `type: "json_schema"`와 스키마를 넣는다(집필 시점 2026-11. 예전 베타 파라미터 `output_format`은 deprecated로 표시되어 있다). 요청 모양은 다음과 같다. 이 코드는 유료 API 키가 필요해 이 책에서 **실행하지 않은 참고 예시**다.

```json
{
  "model": "<공식 문서의 현재 모델 ID>",
  "max_tokens": 512,
  "messages": [{"role": "user", "content": "다음 문의를 분류하세요: 주문 A-1이 3일째 안 와요"}],
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "required": ["category", "urgency", "summary"],
        "properties": {
          "category": {"type": "string", "enum": ["배송", "환불", "계정", "기타"]},
          "urgency": {"type": "string", "enum": ["low", "high"]},
          "summary": {"type": "string"}
        },
        "additionalProperties": false
      }
    }
  }
}
```

구조화 출력이 보장하는 것은 **형식**이지 **내용의 정확성**이 아니다. `category`가 네 값 중 하나라는 것은 보장돼도, 그 분류가 맞는지는 평가(6.4절)로만 안다. 문서가 밝힌 한계도 있다. `minimum`·`maxLength` 같은 수치·길이 제약은 지원하지 않고, `enum` 값의 대소문자는 보장하지 않는다. 그래서 기능을 쓰더라도 **애플리케이션 쪽 검증은 남겨 둔다**.

**실패 처리 정책**: 검증에 실패하면 (1) 실패 이유를 붙여 한두 번 다시 요청하거나 (2) 사람 검토 대기열로 보낸다. 무한 재시도는 비용만 늘린다. 어느 경우든 실패를 로그와 지표로 남겨 비율을 지켜본다.

::example ch6/structured_output.py

해설:

- T-1은 처음부터 스키마에 맞았다.
- T-2의 첫 응답은 설명 문장과 코드 펜스가 섞여 JSON 파싱에 실패했고, 재시도에서 통과했다. 정규식으로 JSON 부분을 오려 내는 우회도 가능하지만 근본 해결은 구조화 출력이나 명확한 형식 지시다.
- T-3은 허용되지 않은 값(`결제`, `urgent`)을 냈다. 재시도에서 분류는 고쳤지만 긴급도는 여전히 틀려 **사람 검토 대기열**로 갔다. 프로그램이 추측으로 값을 채우지 않는다.
- T-4의 첫 응답은 `max_tokens`로 잘렸다. JSON을 고치려 하지 않고 종료 이유만 보고 다시 요청했다. 두 번째 응답의 `High`는 대소문자만 다른 값이라 허용 목록의 `high`로 맞췄다.

## 흔한 오류와 디버깅

- **파싱 실패 시 프로그램 전체 중단**: 한 건의 이상한 출력이 전체 처리를 멈추게 하지 않도록 건별로 격리한다(3.3절의 격리와 같은 원리).
- **스키마 통과 = 정답으로 착각**: 형식 검증과 품질 평가는 별개다.
- **종료 이유 무시**: 잘린 JSON을 억지로 고쳐 쓰면 내용 일부가 사라진 결과가 저장된다.
- **모델 ID·가격 하드코딩**: 모델과 가격은 바뀐다. 설정으로 분리하고(4.3절) 공식 문서의 현재 값을 확인한다.
- **예시 몇 개로 출시**: 데모의 성공 사례는 운영 분포를 대표하지 않는다. 6.4절의 평가셋을 먼저 만든다.

## 이해 확인

::quiz
구조화 출력을 켰더니 `category`가 항상 허용 값 중 하나로 나온다. 동료가 "이제 분류 정확도는 걱정 없다"고 한다. 무엇이 틀렸는가?
::answer
구조화 출력은 형식(스키마 준수)을 제약할 뿐, `배송` 문의를 `환불`로 분류하는 것 같은 내용 오류는 막지 않는다. 정확도는 정답이 붙은 평가셋으로 측정해야 한다(6.4절). 또 문서에 따르면 `refusal`·`max_tokens` 종료나 enum 대소문자 차이처럼 스키마와 어긋나는 경우도 남아 있어 애플리케이션 검증이 필요하다.
::end

::quiz
검증 실패 시 "통과할 때까지 재시도"하도록 구현했다. 운영에서 어떤 문제가 생길 수 있으며 어떻게 바꾸는가?
::answer
특정 입력에서 모델이 계속 같은 이유로 실패하면 무한 반복으로 비용과 지연이 끝없이 늘고, 처리 대기열이 막힌다. 재시도 횟수 상한(예: 1–2회)을 두고, 넘으면 사람 검토로 보내며, 실패율을 지표로 남겨 프롬프트나 스키마 개선의 근거로 쓴다(2.4절의 재시도 예산과 같은 원리).
::end
