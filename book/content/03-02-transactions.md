## 학습 목표와 선수 개념

- 트랜잭션이 보장하는 원자성(모두 또는 전무)을 예제로 확인한다.
- `CHECK`, `UNIQUE`, 복합 기본 키가 애플리케이션 실수를 막는 방식을 이해한다.
- Python `sqlite3`의 `with con:` 블록이 커밋·롤백하는 규칙을 안다.

선수 개념: 3.1절, 예외 처리.

## 현장 상황

고객사의 주문 시스템은 주문 하나에 여러 품목의 재고를 차감한다. 두 번째 품목에서 오류가 나면 첫 번째 품목의 재고만 줄어든 채로 남았다. 몇 주 뒤 창고 실사에서 시스템 재고와 실제 재고가 맞지 않는다는 문제가 나왔다. 데이터 문제처럼 보이지만 원인은 "중간에 실패하면 어떻게 되는가"를 설계하지 않은 코드였다.

## 원리와 용어

**트랜잭션**은 여러 SQL 문을 하나의 작업 단위로 묶는다. 모두 성공하면 **커밋(commit)**해 확정하고, 하나라도 실패하면 **롤백(rollback)**해 시작 전 상태로 되돌린다. 흔히 ACID(원자성·일관성·격리성·지속성)로 요약한다. 이 절은 그중 원자성과 일관성에 집중한다.

SQLite 문서에 따르면 명시적 트랜잭션 밖에서 실행한 문장은 각각 자동으로 트랜잭션이 되어 끝날 때 커밋된다. 여러 문장을 묶으려면 `BEGIN … COMMIT`을 쓴다. 기본 `BEGIN`은 `DEFERRED`로, 첫 읽기·쓰기 때 실제로 시작한다. `BEGIN IMMEDIATE`는 시작하자마자 쓰기 잠금을 잡는다. `BEGIN…COMMIT`은 중첩되지 않으며, 안쪽 단위가 필요하면 `SAVEPOINT`를 쓴다.

Python `sqlite3`의 연결 객체를 `with con:`으로 쓰면, 블록이 예외 없이 끝날 때 커밋하고 예외가 나면 롤백한 뒤 예외를 다시 던진다. 연결을 닫지는 않는다.

**제약**은 트랜잭션과 함께 일관성을 지킨다.

- `CHECK (qty >= 0)`: 재고가 음수가 되는 변경을 거부한다.
- `PRIMARY KEY (order_id, sku)`: 같은 주문에 같은 품목을 두 번 예약하지 못하게 한다. 2.5절의 멱등성 키나 2.6절의 이벤트 ID 중복 방지도 이렇게 DB 제약으로 지키는 것이 가장 확실하다.

- **트랜잭션 없음**: 줄마다 `commit()`하므로 `BOX-S` 차감과 예약 1건이 이미 확정된 뒤 `TAPE`에서 실패했다. 주문은 실패했는데 재고는 줄어든, 바로 현장 상황의 버그다.
- **트랜잭션**: `with con:` 안에서 실패하자 `BOX-S` 차감까지 모두 롤백됐다.
- **정상 예약**은 두 변경이 함께 커밋됐다.
- **중복 예약 시도**는 복합 기본 키가 막았고, 그 블록의 재고 차감도 함께 취소되어 재고가 3으로 유지됐다.
- 예외 메시지는 어떤 제약이 실패했는지 알려 준다. 사용자에게 보여 줄 메시지(예: "재고가 부족합니다")로 바꾸는 일은 애플리케이션이 한다.

## 흔한 오류와 디버깅

- **반복문 안에서 커밋**: 처리 속도를 위해 넣은 `commit()`이 원자성을 깬다. 어떤 단위가 "함께 성공해야 하는가"를 먼저 정한다.
- **외부 호출을 트랜잭션 안에서**: 트랜잭션 안에서 외부 API를 호출하면 잠금을 오래 잡고, 롤백해도 외부 호출은 되돌릴 수 없다. 외부 부작용은 커밋 뒤에 하거나 "보낼 일" 표에 기록한 뒤 별도 작업으로 보낸다.
- **검사 후 쓰기 경쟁**: `SELECT qty`로 확인한 뒤 `UPDATE`하면, 그 사이 다른 요청이 재고를 바꿀 수 있다. 예제처럼 `UPDATE … SET qty = qty - ?`와 `CHECK` 제약으로 DB가 한 번에 판단하게 하거나, 적절한 잠금·격리 수준을 쓴다.
- **자동 커밋 설정 혼동**: Python 3.12부터 `sqlite3.connect(..., autocommit=...)`가 생겼지만 기본값은 아직 이전 동작(`LEGACY_TRANSACTION_CONTROL`)이다. `autocommit=False`로 열면 항상 트랜잭션이 열려 있어, 테이블을 만든 뒤 `commit()`을 빼먹으면 이후 롤백이 테이블 생성까지 되돌린다(`no such table` 오류). 어떤 모드인지 확인하고 설정 단계 뒤에 명시적으로 커밋한다.
- **database is locked**: SQLite는 동시에 쓰기 트랜잭션 하나만 허용한다. 긴 트랜잭션을 줄이고, 쓰기가 많은 서비스는 서버형 DB를 검토한다.

## 이해 확인

::quiz
`with con:` 블록 안에서 `UPDATE`가 성공한 직후 Python 코드에서 `ValueError`가 발생했다(SQL 오류가 아님). 그 `UPDATE`는 확정되는가?
::answer
확정되지 않는다. `with con:`은 블록에서 어떤 예외든 빠져나오면 롤백한다. SQL 오류가 아니어도 같은 트랜잭션의 변경은 모두 취소되고, 예외는 다시 던져진다.
::end

::quiz
"재고 확인 → 결제 API 호출 → 재고 차감"을 하나의 DB 트랜잭션으로 묶었다. 어떤 문제가 생길 수 있는가?
::answer
결제 API가 느리면 그동안 쓰기 잠금을 잡아 다른 주문이 기다린다. 또 결제는 성공했는데 이후 DB 오류로 롤백되면 결제만 남는다(DB 롤백은 외부 결제를 취소하지 못한다). 재고 예약을 먼저 커밋하고, 결제 결과에 따라 예약 확정·해제를 별도 단계로 처리하며, 결제 요청에는 멱등성 키를 쓰는 설계가 낫다.
::end
