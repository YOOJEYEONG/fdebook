## 학습 목표와 선수 개념

- 1장의 문제 정의와 수용 기준을 실제 설계 문서로 옮긴다.
- 2–6장의 기술이 시스템의 어느 경계에 들어가는지 지도로 그린다.
- 개인정보 없이 개발·평가할 수 있는 합성 데이터를 결정적으로 만든다.

선수 개념: 1–6장 전체. 이 장은 새 개념보다 **연결**을 다룬다.

## 현장 상황

1.2절의 물류·유통 고객사 두 곳(가나물류, 다라상사)이 같은 상담 플랫폼을 쓴다. 플랫폼은 새 문의가 생길 때마다 웹훅을 보낸다. 요청은 "문의를 자동으로 팀별 분류하고, 고객사별로 조회할 수 있게 해 달라"이다. 제약은 세 가지다. 웹훅 주소는 인터넷에 열려 있고, 이메일 같은 개인정보는 원문으로 저장하지 않으며, 두 고객사의 데이터는 서로 보이면 안 된다.

## 원리와 용어

### 문제 정의와 수용 기준(1.2·1.3절 적용)

- 문제: 문의가 수작업으로 분류되어 첫 응답이 늦고, 긴급 문의가 묻힌다.
- 범위 안: 웹훅 수신, 저장, 자동 분류(팀·긴급도), 고객사별 조회 API.
- 범위 밖: 고객에게 자동 답장, 환불 자동 처리.
- 수용 기준: 자동 배정 비율 70% 이상, 자동 배정 중 오배정 5% 이하, 모든 분류 재현율 0.7 이상, 긴급 누락 0건. **확신이 낮으면 사람 검토로 보낸다**(틀린 자동 배정보다 사람 검토가 낫다).

### 구성과 경계

```text
상담 플랫폼 ──웹훅(POST, HMAC 서명)──▶ [수신] 서명·시각 확인(2.6)
                                          │ 이벤트 ID 중복 제거(2.5, 3.2)
                                          ▼
                                       [가명화] 이메일 → HMAC 가명(3.5)
                                          ▼
                                       [분류] 규칙 → (불확실하면) 모델 → 검증 실패면 사람(6.1)
                                          ▼
                                       [저장] SQLite, 제약·트랜잭션(3.1, 3.2)
                                          ▼
고객사 화면 ◀──GET /inquiries(Bearer 토큰 → 테넌트)── [조회] 테넌트 조건 강제(2.2, 5.5)
```

경계마다 신뢰할 수 없는 입력이 들어온다: 웹훅 본문(외부), 조회 요청의 매개변수(사용자), 모델 출력(6장). 각 경계에 검증이 하나씩 있다.

### 데이터 모델

- `events(event_id PRIMARY KEY)`: 처리한 웹훅 이벤트. 기본 키가 중복 처리를 막는다.
- `inquiries`: 문의. `tenant`(고객사), `customer`(가명), `text`, `category`(허용 값 CHECK), `urgent`(0/1), `route`(`rule`/`model`/`human`).
- 이메일 원문 열은 **아예 없다**. 저장하지 않는 것이 가장 확실한 보호다.
- `route`를 저장해 두면 나중에 경로별 품질과 비용을 따로 잴 수 있다(6.4·6.6절).

### 합성 데이터

실제 문의를 쓰지 않고, 분류별 문장 템플릿과 무작위 주문 번호로 문의 60건을 만든다. 씨앗(seed)을 고정해 누가 언제 실행해도 같은 데이터가 나온다. 정답(`gold_category`, `gold_urgent`)을 함께 만들어 평가(8.3절)에 쓴다. 합성 데이터는 실제 분포를 대표하지 못한다는 한계가 있다. 8.3절에서 그 한계를 직접 확인한다.

## 흔한 오류와 디버깅

- **설계 없이 코드부터**: 경계와 신뢰 수준을 먼저 그리지 않으면 검증이 빠진 경로가 생긴다.
- **운영 데이터를 개발에 복사**: 합성 데이터로 시작하고, 실제 데이터 평가는 고객사 환경 안에서 한다.
- **무작위 데이터에 씨앗 없음**: 실행마다 결과가 달라 버그 재현과 출력 비교가 불가능하다.
- **균형 잡힌 합성 데이터의 지표를 운영 기대치로 보고**: 분포가 다르면 지표도 달라진다.

## 이해 확인

::quiz
설계도에서 "조회 API의 테넌트를 어디서 얻는가"는 왜 중요한가? 잘못 설계한 예와 함께 설명하라.
::answer
테넌트는 데이터 경계 그 자체다. 잘못된 예는 `GET /inquiries?tenant=가나물류`처럼 요청 매개변수로 테넌트를 받는 것이다. 다른 고객사 사용자가 값만 바꿔 남의 데이터를 볼 수 있다(5.5절의 BOLA). 테넌트는 인증된 토큰에서만 얻고, 모든 질의에 그 조건을 강제한다.
::end

::quiz
`inquiries` 표에 `email` 열을 두고 "화면에서만 가리자"는 의견이 나왔다. 이 설계의 수용 기준과 제약에 비추어 반대 근거를 들어라.
::answer
제약은 "개인정보 원문을 저장하지 않는다"이다. 화면 마스킹(3.5절)은 표시만 가릴 뿐, 저장된 원문은 백업·로그·DB 접근 권한자·유출 사고에 그대로 노출된다. 반복 문의 집계라는 목적은 HMAC 가명으로 충분히 달성되므로, 원문 저장은 목적에 필요한 범위를 넘는다.
::end
