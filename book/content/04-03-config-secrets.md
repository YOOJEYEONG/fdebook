## 학습 목표와 선수 개념

- 설정과 코드를 분리하는 이유를 Twelve-Factor의 기준으로 설명한다.
- 환경 변수에서 설정을 읽고 시작 단계에서 검증하는 코드를 쓴다.
- 비밀값이 로그·오류·저장소로 새는 경로를 막는다.

선수 개념: 환경 변수 개념(터미널에서 `NAME=value 명령`).

## 현장 상황

PoC를 고객 개발 환경에서 운영 환경으로 옮기는 날, 코드에 박혀 있던 DB 주소가 개발 DB를 가리키고 있었다. 게다가 저장소 기록에는 테스트용 API 토큰이 커밋되어 있었고, 그 토큰은 운영에서도 유효했다. 토큰을 폐기하고 새로 발급하는 데 하루가 걸렸다. 2.2절에서 본 것처럼 Bearer 토큰은 가진 사람이면 누구나 쓸 수 있다.

## 원리와 용어

**설정(config)**은 Twelve-Factor App(표준이 아니라 널리 쓰이는 커뮤니티 방법론)의 정의로 "배포마다 달라질 수 있는 모든 것"이다. DB 주소, 외부 서비스 자격 증명, 호스트 이름, 시간 제한 값 등이다. 같은 코드가 개발·스테이징·운영에서 다른 설정으로 돌아야 한다. Twelve-Factor는 설정을 **환경 변수**에 두라고 권하며, "지금 당장 코드를 공개해도 자격 증명이 새지 않는가"를 분리 여부의 시험으로 제시한다.

**비밀값(secret)**은 설정 중에서도 노출되면 피해가 생기는 값이다(API 토큰, DB 비밀번호, 서명 키, 3.5절의 가명화 키). 원칙:

- 코드·저장소·컨테이너 이미지에 넣지 않는다. `.env` 파일을 쓴다면 `.gitignore`에 넣는다.
- 운영에서는 클라우드·플랫폼의 비밀 저장소나 배포 도구의 비밀 관리 기능으로 주입한다. 환경 변수는 코드와 분리하는 수단이지 그 자체로 안전한 보관소는 아니다(같은 프로세스·자식 프로세스·덤프에서 읽힐 수 있다).
- 로그, 오류 메시지, 디버그 출력에 찍히지 않게 한다.
- 최소 권한·짧은 수명·교체 가능하게 발급한다. 유출을 의심하면 즉시 폐기하고 새로 발급한다.

**시작 시 검증(fail fast)**: 필수 설정이 없거나 형식이 틀리면 프로세스가 시작조차 하지 않게 한다. 새벽에 첫 요청이 들어왔을 때 터지는 것보다, 배포 순간 실패해 롤백되는 편이 훨씬 싸다.

## 예제: 설정 읽기와 검증

실행 명령에서 환경 변수를 넘긴다. 토큰은 예제용 가짜 값이다.

::example ch4/config.py | APP_ENV=staging DATABASE_URL=sqlite:///tmp/tickets.db API_TOKEN=example-not-a-real-token python3 examples/ch4/config.py

해설:

- `Settings`를 통째로 출력해도 토큰은 `Secret(***)`으로 나온다. `Secret` 클래스가 `repr`과 `str`을 가리기 때문이다. 실수로 설정 객체를 로그에 남겨도 값이 새지 않는다.
- 토큰의 존재와 길이처럼 값이 아닌 정보만으로도 "설정이 들어왔는지"를 확인할 수 있다.
- 필수 값 누락, 허용되지 않은 `APP_ENV`, 숫자가 아닌 시간 제한은 모두 시작 단계에서 이유와 함께 거부된다.
- `REQUEST_TIMEOUT_S`처럼 안전한 기본값이 있는 설정은 생략할 수 있게 했다. 비밀값과 환경 이름은 기본값을 두지 않는다. 기본값이 있으면 운영에 개발용 값이 조용히 들어간다.

## 흔한 오류와 디버깅

- **비밀값이 커밋됨**: 다음 커밋에서 지워도 기록에 남는다. 먼저 폐기·재발급하고, 그 뒤 기록 정리 여부를 판단한다. 저장소에 비밀값 탐지 도구를 켠다.
- **오류 메시지에 값 포함**: `f"연결 실패: {database_url}"`의 주소에 비밀번호가 들어 있을 수 있다. 값 대신 설정 이름을 적는다.
- **환경 이름으로 분기하는 코드**: `if env == "prod":`가 곳곳에 퍼지면 스테이징에서 운영 동작을 시험할 수 없다. 동작 차이는 개별 설정값으로 표현한다.
- **프로세스 목록과 셸 기록**: 명령줄 인자로 비밀값을 넘기면 다른 사용자가 프로세스 목록에서 볼 수 있고 셸 기록에도 남는다. 운영에서는 비밀 저장소나 파일 마운트를 쓴다.

## 이해 확인

::quiz
고객사 보안 담당자가 "토큰이 로그에 남은 적이 있는지 확인해 달라"고 한다. 무엇을 검색하고, 발견하면 어떤 순서로 대응하는가?
::answer
토큰 값 자체로 로그를 검색하면 검색 시스템에 또 남을 수 있으므로, 토큰의 앞 몇 글자(접두어)나 `Authorization` 헤더가 기록되는 필드를 기준으로 찾는다. 발견하면 (1) 토큰을 폐기·재발급하고 (2) 해당 로그의 접근 범위와 보관 기간을 확인해 삭제 또는 접근 제한을 하고 (3) 로그를 남긴 코드를 고쳐 헤더를 가리고 (4) 고객에게 영향 범위를 보고한다.
::end

::quiz
`REQUEST_TIMEOUT_S`에는 기본값이 있고 `DATABASE_URL`에는 없다. 이 차이를 정한 기준은 무엇인가?
::answer
기본값이 틀렸을 때의 피해다. 시간 제한 5초는 어느 환경에서나 합리적이고 틀려도 성능 문제에 그친다. DB 주소에 기본값이 있으면 설정을 빠뜨린 운영 배포가 개발 DB에 붙는 것처럼 데이터 사고로 이어진다. 그런 값은 기본값 없이 필수로 두어 시작을 막는다.
::end
