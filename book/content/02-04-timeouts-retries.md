## 학습 목표와 선수 개념

- 모든 원격 호출에 시간 제한이 필요한 이유를 설명한다.
- 재시도해도 되는 실패와 안 되는 실패를 상태 코드와 메서드로 구분한다.
- 상한이 있는 지수 백오프와 지터, `Retry-After`를 따르는 재시도 함수를 작성한다.

선수 개념: 2.1·2.2절, 예외 처리.

## 현장 상황

고객사 시스템이 외부 배송 조회 API를 호출한다. 어느 날 배송사 API가 느려지자 고객사 서버의 작업자 스레드가 모두 응답을 기다리며 멈췄고, 배송과 무관한 화면까지 열리지 않았다. 시간 제한이 없었기 때문이다. 급하게 "실패하면 즉시 3번 재시도"를 넣었더니, 이번에는 배송사가 회복하려는 순간마다 평소의 몇 배 요청이 몰려 회복이 더 늦어졌다.

## 원리와 용어

### 시간 제한(timeout)

응답이 오지 않으면 언젠가 포기해야 한다. 기다리는 동안 스레드·연결·메모리가 묶이기 때문이다. AWS가 게시한 엔지니어링 글(Builders' Library, 표준 문서가 아니라 실무 경험 정리)은 모든 원격 호출에 시간 제한을 두라고 권하며, 너무 짧으면 정상 요청까지 실패로 만들고 너무 길면 자원을 오래 묶는다고 설명한다. 실무에서는 상대 서비스의 정상 지연 분포(5.3절의 p99 등)를 보고 정한다.

### 무엇을 재시도할까

- **재시도할 만한 실패**: 연결 실패, 시간 초과, 429(요청이 너무 많음), 502·503·504(게이트웨이·일시적 불가). 기다리면 나아질 가능성이 있다.
- **재시도하면 안 되는 실패**: 400·401·403·404·422. 같은 요청은 같은 이유로 또 실패한다.
- **메서드도 본다**: RFC 9110에서 `GET`·`PUT`·`DELETE`와 안전한 메서드는 **멱등**이다. 같은 요청을 여러 번 보내도 의도한 효과가 한 번 보낸 것과 같다. `POST`는 멱등이 아니어서, 응답만 잃어버린 결제 요청을 다시 보내면 두 번 결제될 수 있다. 부작용이 있는 요청은 2.5절의 멱등성 키가 있을 때만 재시도한다.

### 백오프와 지터

실패 직후 바로 다시 보내면 아직 회복하지 못한 서버에 부하만 더한다. **지수 백오프**는 시도할 때마다 기다리는 시간을 0.5초, 1초, 2초, 4초…로 늘린다. 끝없이 늘지 않도록 **상한**을 둔다. 그런데 많은 클라이언트가 같은 순간 실패하면 같은 간격으로 다시 몰려온다. **지터**는 기다리는 시간에 무작위성을 더해 재시도를 흩뜨린다. 이 예제는 0과 백오프 값 사이에서 고르게 뽑는 방식(full jitter)을 쓴다.

**Retry-After** 헤더(RFC 9110 10.2.3)는 서버가 "이만큼 기다린 뒤 오라"고 직접 알려 주는 값이다. RFC 6585는 429 응답에 이 헤더를 넣을 수 있다고 정한다. 있으면 자체 계산보다 우선한다.

### 재시도는 한 곳에서

여러 계층이 각자 재시도하면 시도 횟수가 곱해진다. AWS Builders' Library는 5개 계층이 각각 3번씩 시도하면 맨 아래 DB에 걸리는 부하가 3의 5제곱인 243배가 된다는 예를 든다. 재시도는 한 계층에서만 하고 나머지는 빠르게 실패를 전달한다.

## 예제: 503, 429, 응답 없음

서버는 `/orders`에 차례로 503, 429(`Retry-After: 2`), 200을 돌려주고, `/slow`는 1초 동안 응답하지 않는다. 예제에서는 실제로 잠들지 않고 기다릴 시간만 기록한다.

::example ch2/retry_backoff.py

해설:

- 503에는 계산한 백오프(0.16초, 지터 때문에 0~0.5초 사이 값)를, 429에는 서버가 말한 2초를 쓴다.
- `/slow`는 시간 제한 0.3초에 걸린다. 최대 시도 횟수에 이르면 더 기다리지 않고 포기를 알린다. 마지막 시도 뒤에 기다리는 것은 낭비다.
- 404 같은 오류는 `RETRYABLE`에 없으므로 곧바로 예외를 다시 던진다.
- 예제의 `random.Random(7)`은 출력을 책과 똑같이 맞추기 위한 것이다. 실제 코드에서 모든 프로세스가 같은 씨앗을 쓰면 지터가 사라진다.

## 흔한 오류와 디버깅

- **시간 제한 없음**: 라이브러리 기본값이 "무한"인 경우가 많다. Python `urllib`도 `timeout`을 주지 않으면 소켓 기본값을 따른다.
- **POST를 그냥 재시도**: 중복 주문·중복 결제의 대표 원인이다.
- **재시도 예산 없음**: 시도 횟수뿐 아니라 전체 소요 시간 상한도 둔다. 사용자가 이미 떠난 요청을 계속 재시도하지 않는다.
- **로그에 시도 정보 없음**: 몇 번째 시도에서 어떤 이유로 실패했는지 남겨야 "가끔 느리다"를 분석할 수 있다.
- **Retry-After의 날짜 형식**: 값이 초가 아니라 HTTP 날짜일 수도 있다. 예제는 숫자만 처리하고 그 외에는 자체 백오프로 대신한다.

## 이해 확인

::quiz
3개 계층(웹 → API → DB 호출)이 각각 실패 시 최대 4번 시도하도록 설정되어 있다. DB가 완전히 멈췄을 때, 사용자 요청 하나가 DB에 보내는 최대 시도 횟수는?
::answer
4 × 4 × 4 = 64번. 각 계층의 한 번 시도가 아래 계층의 4번 시도로 이어지므로 곱해진다. 재시도는 한 계층에서만 하고 나머지 계층은 실패를 바로 전달해야 한다.
::end

::quiz
`PUT /tickets/7/status`(본문 `{"status": "closed"}`)가 시간 초과로 실패했다. 재시도해도 되는가? `POST /tickets/7/comments`라면?
::answer
`PUT`은 대상 상태를 이 값으로 바꾸는 멱등 메서드이므로 여러 번 보내도 결과가 같아 재시도해도 된다. `POST`로 댓글을 추가하는 요청은 멱등이 아니어서, 첫 요청이 실제로 처리됐다면 재시도가 댓글을 하나 더 만든다. 멱등성 키를 지원하는 경우에만 재시도한다.
::end

::quiz
지터 없이 지수 백오프만 쓰면 어떤 상황에서 문제가 되는가?
::answer
많은 클라이언트가 같은 장애로 동시에 실패하면 모두 같은 간격(0.5초, 1초, 2초…)으로 다시 요청해, 회복 중인 서버에 같은 순간 요청이 몰린다. 지터는 각 클라이언트의 대기 시간을 흩어 이 동기화를 깬다.
::end
