## 학습 목표와 선수 개념

- 청중마다 알고 싶은 것(결정, 위험, 운영 부담, 일의 변화)을 구분해 설명을 바꾼다.
- 결론 → 근거 → 한계 → 다음 결정 순서로 짧게 설명한다.
- 실패 경로를 포함한 데모 대본을 쓴다.

선수 개념: 1장. 데모 내용으로 2·6장의 예제를 사용한다.

## 현장 상황

분류 시스템 파일럿 결과를 보고하는 자리에 운영팀장, 재무 임원, IT 리드, 보안 담당이 함께 앉았다. FDE가 프롬프트 구조와 F1 점수부터 설명하자 임원은 시계를 보고, 보안 담당은 "그래서 고객 데이터는 어디로 가나요?"라고 끼어든다. OpenAI FDE 공고는 엔지니어, 제품팀, 고객 이해관계자와 명확히 소통하는 능력을, Anthropic 공고는 다양한 이해관계자에게 기술 개념을 전달하는 능력을 요구한다.

## 원리와 용어

**청중별 질문**: 같은 시스템도 사람마다 묻는 것이 다르다.

| 청중 | 알고 싶은 것 | 설명의 중심 |
|---|---|---|
| 현업 사용자(상담원) | 내 일이 어떻게 바뀌나, 틀리면 어떻게 하나 | 화면 흐름, 수정 방법, 예외 처리 |
| 임원·구매자 | 효과와 비용, 무엇을 결정해야 하나 | 수용 기준 결과, 비용, 위험, 결정 사항 |
| IT·운영 | 무엇을 운영해야 하나, 장애 때 무엇을 하나 | 구성, 의존성, 모니터링, 롤백, 런북 |
| 보안·법무 | 데이터가 어디로 가나, 권한은 어떻게 통제되나 | 데이터 흐름, 보관, 접근 통제, 로그 |

**결론 먼저**: 바쁜 청중에게는 "결론 → 근거(숫자) → 한계 → 지금 결정할 것" 순서로 말한다. 세부는 질문을 받으면 꺼낸다. Google Technical Writing 과정이 강조하는 "독자를 정하고, 그 독자가 필요한 것만 쓴다"는 원칙은 말로 설명할 때도 같다.

**정확한 단어**: "AI가 판단합니다"보다 "규칙으로 확실한 건은 바로 배정하고, 나머지는 모델이 분류한 뒤 형식 검사를 통과하지 못하면 사람에게 넘깁니다". 과장된 표현("완벽하게", "항상")은 신뢰를 잃게 한다. 측정한 범위만 주장한다.

**데모의 목적**: 데모는 기능 자랑이 아니라 **결정을 돕는 증거**다. 좋은 데모는 (1) 청중의 실제 데이터나 그와 비슷한 합성 데이터로 (2) 대표 사례와 함께 **실패 사례**를 보여 주고 (3) 실패했을 때 시스템이 어떻게 행동하는지(사람 검토로 넘김, 경보) 보여 준다. 실패를 숨긴 데모는 운영 첫날 신뢰를 잃는다.

## 예제: 같은 결과, 두 가지 설명(분석 사례)

### 나쁜 설명(임원 대상)

> "프롬프트를 few-shot으로 바꾸고 JSON 스키마를 강제해서 매크로 F1이 0.79에서 0.82로 올랐고요, 계정 클래스는 recall이 좀 떨어졌는데 temperature를 조정하면…"

용어가 많고, 결정할 것이 없고, 좋은 소식과 나쁜 소식이 섞여 결론을 알 수 없다.

### 좋은 설명(임원 대상, 1분)

> "결론: 운영 전환은 2주 미루기를 제안합니다. 근거: 합의한 기준 4개 중 3개를 넘었습니다. 첫 응답 시간 p90이 95분에서 26분으로 줄었습니다. 한계: 긴급 문의 1건이 일반 대기열로 갔습니다. 기준은 0건입니다. 원인은 찾았고 수정 중입니다. 결정 요청: 2주 연장과, 그 기간 상담팀장 1명의 검수 시간을 승인해 주십시오."

### 같은 결과를 보안 담당에게

> "문의 본문은 고객사 클라우드 계정 안의 모델 엔드포인트로만 갑니다. 저장되는 것은 분류 결과와 가명화한 고객 식별자뿐입니다. 모델 응답은 형식 검사를 거치고, 발송·환불 같은 쓰기 도구는 이 기능에 없습니다. 접근 로그는 90일 보관합니다."

### 데모 대본(10분)

| 시간 | 장면 | 보여 줄 것 |
|---|---|---|
| 0–1분 | 문제 | 1.2절의 데이터(배송 조회 41%, 건당 4분) |
| 1–4분 | 대표 흐름 | 배송 문의가 자동 배정되고 상담 화면에 배송 상태가 뜨는 모습 |
| 4–6분 | 실패 흐름 | 애매한 문의가 사람 검토 대기열로 가는 모습, 배송사 API 시간 초과 시 "확인 불가" 표시 |
| 6–8분 | 숫자 | 수용 기준 판정 표(1.3절), 평가 결과(6.4절) |
| 8–10분 | 결정 | 남은 위험, 운영 전환 체크리스트(1.4절), 요청할 결정 |

## 흔한 오류와 디버깅

- **모두에게 같은 설명**: 청중별로 설명을 준비하거나, 공통 결론 뒤에 청중별 부록을 둔다.
- **용어를 정의 없이 사용**: F1, RAG, p90 같은 말은 첫 등장에 한 문장으로 풀거나 쓰지 않는다.
- **성공 사례만 데모**: 운영에서 처음 실패를 본 고객은 시스템을 믿지 않게 된다.
- **라이브 데모 의존**: 네트워크·외부 API 문제로 데모가 멈출 수 있다. 녹화본과 로컬 대체 데이터를 준비한다.
- **질문에 추측으로 답함**: 모르면 "확인해서 오늘 안에 답하겠다"고 하고 실제로 답한다.

## 이해 확인

::quiz
IT 리드가 "이거 운영하려면 우리 팀이 뭘 해야 하죠?"라고 묻는다. 7.3절을 미리 보지 않고, 답에 들어가야 할 항목 네 가지를 들어라.
::answer
예: (1) 구성과 의존성: 어떤 서비스·DB·외부 API가 있는지 (2) 모니터링과 경보: 무엇을 보고 언제 알림이 오는지 (3) 장애 대응과 롤백 절차: 경보별 첫 조치 (4) 정기 작업: 비밀값 교체, 평가 재실행, 백업. 각 항목에 예상 업무량(주당 시간)을 붙이면 결정에 도움이 된다.
::end

::quiz
임원 보고에서 "AI가 문의를 정확하게 분류합니다"라는 문장을 쓰려 한다. 무엇이 문제이며 어떻게 고치는가?
::answer
"정확하게"는 측정 범위와 한계를 숨긴 과장이다. 예: "합의한 평가셋 200건에서 클래스별 재현율 0.78–0.95였고, 확신이 낮은 약 12%는 사람 검토로 넘깁니다. 계정 문의가 가장 약해 개선 중입니다." 처럼 측정한 숫자, 범위, 예외 처리, 약점을 함께 말한다.
::end
