## 학습 목표와 선수 개념

- 단위 테스트와 통합(계약) 테스트가 각각 무엇을 잡는지 구분한다.
- `unittest`로 경계값 테스트와 격리된 통합 테스트를 작성한다.
- 버그를 고칠 때 재현 테스트를 먼저 쓰는 습관을 들인다.

선수 개념: 4.1절의 `tickets_api.py`.

## 현장 상황

고객 현장에서 "제목이 120자인 문의가 저장되지 않는다"는 보고가 왔다. 확인해 보니 누군가 검증 조건을 `< 120`으로 바꿔 놓았다. 문서에는 "최대 120자"라고 되어 있다. 경계값 테스트가 하나만 있었어도 변경 순간에 잡혔을 버그다. FDE는 고객 인프라에서 일하며 다른 팀의 코드와 엮이는 일이 많아서, 내가 만든 부분이 계약을 지킨다는 증거를 테스트로 남겨 두어야 한다.

## 원리와 용어

- **단위 테스트**: 함수 하나를 네트워크·DB 없이 시험한다. 빠르고(밀리초) 실패 원인이 좁다. 검증 규칙, 계산, 변환처럼 순수한 로직에 쓴다.
- **통합 테스트**: 여러 부분을 실제로 연결해 시험한다. 이 절의 계약 테스트는 실제 HTTP 서버와 DB를 띄워 상태 코드·헤더·본문 형식이 계약대로인지 확인한다. 느리지만 "조립했을 때"의 문제를 잡는다.
- **경계값**: 오류는 경계에서 많이 난다. 최대 120자라면 120자(통과)와 121자(실패)를 둘 다 시험한다.
- **격리**: 테스트끼리 상태를 공유하면 실행 순서에 따라 결과가 바뀐다. 예제는 `setUp`마다 새 메모리 DB와 서버를 만든다.
- **재현 테스트 먼저**: 버그 보고를 받으면 먼저 그 버그로 실패하는 테스트를 쓰고, 고친 뒤 통과를 확인한다. 같은 버그가 돌아오는 것을 막는다.

어떤 테스트를 얼마나 쓸지는 비용과 위험의 문제다. 계약 경계(외부와 만나는 곳)와 돈·개인정보가 걸린 로직에 먼저 투자한다.

## 예제: 7개의 테스트

::example ch4/test_tickets_api.py

평소에는 표준 실행기로 돌린다. 출력 끝에 소요 시간과 결과 요약이 나온다.

```bash
python3 -m unittest -v examples/ch4/test_tickets_api.py
```

해설:

- `ValidateTest`는 4.1절의 `validate`만 시험한다. 120자/121자 경계, 모든 위반을 한 번에 보고하는지, 타입 오류를 확인한다.
- `ApiContractTest`는 실제 서버에 요청한다. 생성 후 같은 ID로 읽은 값이 생성 응답과 같은지, 오류가 `application/problem+json`인지, 없는 ID가 404인지 본다.
- 통합 테스트 3개는 단위 테스트 4개보다 훨씬 느리다(서버 시작·종료 때문). 그래서 세부 규칙은 단위 테스트로, 연결과 형식은 소수의 통합 테스트로 나눈다.
- 이 파일을 직접 실행하면 책의 출력과 비교할 수 있도록 소요 시간을 빼고 결과만 출력한다. 시험하는 내용은 표준 실행기와 같다.

## 흔한 오류와 디버깅

- **테스트가 순서에 의존**: 단독으로는 통과하는데 전체로 돌리면 실패하면 공유 상태(전역 변수, 같은 DB 파일, 고정 포트)를 의심한다.
- **시간·무작위성**: 현재 시각이나 난수에 의존하는 코드는 그 값을 인자로 받게 바꿔 테스트에서 고정한다(2.4절 예제의 `random.Random(7)`).
- **외부 API 직접 호출**: 테스트가 고객사 운영 API를 부르면 느리고, 불안정하며, 실제 데이터를 바꿀 수 있다. 이 책의 예제처럼 로컬 가짜 서버를 띄운다.
- **"가끔 실패"를 무시**: 불안정한 테스트는 진짜 버그를 숨긴다. 2.2절 예제도 반복 실행으로 연결 재설정 버그를 찾았다. 여러 번 반복 실행해 재현한다(5.2절).

## 이해 확인

::quiz
`validate`의 길이 검사를 `len(value) >= rule["max_length"]`로 잘못 바꿨다. 예제의 어느 테스트가 실패하며 어떤 메시지를 기대할 수 있는가?
::answer
`test_subject_length_boundary`가 실패한다. 120자 제목에 대해 빈 목록(`[]`)을 기대했는데 `최대 120자` 오류가 돌아오므로 `assertEqual`이 두 값을 보여 주며 실패한다. 121자만 시험했다면 이 버그를 잡지 못했다. 경계 양쪽을 시험하는 이유다.
::end

::quiz
통합 테스트가 매번 고정 포트 8080으로 서버를 띄운다. CI에서 테스트를 병렬로 돌리자 가끔 실패한다. 원인과 해결은?
::answer
여러 테스트(또는 다른 프로세스)가 같은 포트를 동시에 쓰려다 "이미 사용 중" 오류가 난다. 포트 0으로 띄워 운영체제가 빈 포트를 고르게 하고, 실제 포트는 `server.server_address[1]`로 읽는다. 예제가 이 방식을 쓴다.
::end
