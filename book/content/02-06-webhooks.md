## 학습 목표와 선수 개념

- 폴링과 웹훅의 차이, 웹훅의 전달 특성(재전송, 순서 보장 없음)을 설명한다.
- HMAC-SHA256 서명을 원시 본문으로 검증하고 상수 시간 비교를 쓴다.
- 타임스탬프로 오래된 요청을 막고 이벤트 ID로 중복 처리를 막는다.

선수 개념: 2.1·2.2·2.5절, 바이트와 문자열의 차이.

## 현장 상황

고객사가 상담 플랫폼의 "티켓 생성" 웹훅을 받아 사내 시스템에 기록하려 한다. 웹훅 주소는 인터넷에 열려 있어야 하므로, 누구든 그 주소로 가짜 이벤트를 보낼 수 있다. 실제로 테스트 중 같은 이벤트가 두 번 들어와 티켓이 중복 생성되기도 했다. FDE는 "진짜 플랫폼이 보낸 것인지", "중간에 바뀌지 않았는지", "이미 처리한 것인지"를 모두 확인하는 수신부를 만들어야 한다.

## 원리와 용어

**웹훅**: 이벤트가 생기면 상대 서비스가 우리 주소로 HTTP POST를 보내는 방식이다. 우리가 주기적으로 "새 것 있어?"라고 묻는 **폴링**보다 빠르고 요청이 적다. 대신 다음을 전제로 설계해야 한다.

- **같은 이벤트가 여러 번 올 수 있다**: 보내는 쪽은 우리 응답을 못 받으면 다시 보낸다. Stripe 문서도 같은 이벤트가 두 번 이상 올 수 있으니 처리한 이벤트 ID를 기록해 중복을 거르라고 안내한다.
- **순서가 보장되지 않는다**: "수정" 이벤트가 "생성"보다 먼저 올 수도 있다.
- **빨리 응답해야 한다**: 무거운 처리를 하다 시간 초과가 나면 보내는 쪽이 실패로 보고 재전송한다. 검증·기록만 하고 2xx를 돌려준 뒤 나머지는 큐에서 처리한다.

**HMAC 서명**: 보내는 쪽과 받는 쪽만 아는 비밀값(secret)으로 본문에 HMAC-SHA256을 계산해 헤더에 담는다. 받는 쪽이 같은 계산을 해서 값이 같으면, 비밀값을 아는 쪽이 보냈고 본문이 바뀌지 않았다는 뜻이다. GitHub은 `X-Hub-Signature-256: sha256=<16진수>` 헤더를, Stripe는 `Stripe-Signature: t=<시각>,v1=<서명>` 헤더를 쓴다. 이름과 형식은 서비스마다 다르므로 각 서비스 문서를 따른다.

검증할 때 지킬 점:

- **원시 바이트로 검증한다**: 서명은 보낸 바이트 그대로에 대해 계산됐다. 프레임워크가 JSON을 파싱했다가 다시 직렬화하면 공백·키 순서가 바뀌어 검증이 실패한다(Stripe 문서가 경고하는 대표 원인).
- **상수 시간 비교**: `==`는 처음 다른 글자에서 멈추므로 비교 시간 차이로 정답을 한 글자씩 추측하는 타이밍 공격의 여지가 있다. Python은 `hmac.compare_digest`를, GitHub 문서도 상수 시간 비교 함수를 권한다.
- **타임스탬프를 서명에 포함**: 시각을 서명 대상에 넣고 허용 시간(예제는 5분)을 넘은 요청을 거절하면, 가로챈 요청을 나중에 다시 보내는 재전송 공격을 줄인다.

## 예제: 여섯 가지 수신 상황

보내는 쪽은 `"타임스탬프.본문"`에 서명한다. 받는 쪽 `receive`는 헤더 확인 → 시각 확인 → 서명 비교 → 중복 확인 순으로 처리한다.

::example ch2/webhook_verify.py

해설:

- 재전송된 같은 이벤트는 200으로 답하되 처리하지 않는다. 4xx나 5xx로 답하면 보내는 쪽이 계속 재전송한다.
- 본문 한 글자(`T-7`→`T-9`)만 바뀌어도, 비밀값이 달라도 서명이 맞지 않는다.
- 마지막 줄은 내용은 같지만 들여쓰기가 다른 JSON이다. 의미가 같아도 바이트가 달라 실패한다. 그래서 파싱 **전에** 검증한다.
- 서명이 틀렸을 때 예제는 401을 쓴다. 보내는 쪽 입장에서는 어떤 4xx든 실패이므로, 실패 이유는 응답보다 우리 쪽 로그에 자세히 남긴다.

## 흔한 오류와 디버깅

- **비밀값 혼동**: 테스트용과 운영용, 엔드포인트별 비밀값이 다르다. 검증이 모두 실패하면 먼저 어떤 비밀값을 쓰는지 확인한다(값 자체를 로그에 찍지 않는다).
- **본문이 이미 파싱됨**: 미들웨어가 본문을 먼저 읽었는지 확인한다.
- **시계 차이**: 서버 시계가 틀리면 정상 요청도 "오래됨"으로 거절된다. NTP 동기화를 확인한다.
- **중복 기록을 메모리에만 둠**: 서버가 재시작하거나 여러 대면 중복을 못 막는다. DB의 고유 제약으로 이벤트 ID를 저장한다(8.2절).
- **검증 없이 이벤트의 데이터를 신뢰**: 서명이 맞더라도 이벤트가 가리키는 자원을 API로 다시 조회해 최신 상태를 확인하는 편이 안전한 경우가 많다(순서 문제도 함께 해결된다).

## 이해 확인

::quiz
웹훅 처리 중 DB 저장에 3초가 걸리고 보내는 쪽의 시간 제한이 2초다. 무슨 일이 생기며 어떻게 고치는가?
::answer
보내는 쪽은 2초 뒤 실패로 판단해 같은 이벤트를 재전송하고, 우리는 같은 이벤트를 여러 번 처리하게 된다. 서명 검증과 이벤트 ID 기록만 빠르게 하고 2xx를 반환한 뒤, 실제 처리는 큐나 백그라운드 작업으로 넘긴다. 이벤트 ID 중복 검사로 재전송도 막는다.
::end

::quiz
`if expected == received:`를 `hmac.compare_digest(expected, received)`로 바꾸는 이유는?
::answer
`==`는 처음 다른 문자에서 비교를 멈추므로 일치하는 앞부분이 길수록 시간이 조금 더 걸린다. 공격자가 응답 시간을 측정해 서명을 한 글자씩 맞춰 갈 여지가 생긴다. `compare_digest`는 내용에 따라 일찍 끝나지 않도록 설계되어 이 정보를 흘리지 않는다.
::end

::quiz
서명은 맞지만 이벤트 순서가 "티켓 수정(10:05)"이 "티켓 생성(10:00)"보다 먼저 도착했다. 어떻게 처리하겠는가?
::answer
수정 이벤트를 받았는데 티켓이 아직 없다면 버리지 말고, (1) 상대 API로 해당 티켓의 현재 상태를 조회해 저장하거나 (2) 이벤트에 들어 있는 시각·버전을 저장된 값과 비교해 더 새로운 것만 반영한다. 나중에 생성 이벤트가 오면 이미 더 새로운 상태가 있으므로 덮어쓰지 않는다.
::end
