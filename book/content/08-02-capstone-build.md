## 학습 목표와 선수 개념

- 앞 장의 부품(서명 검증, 트랜잭션, 가명화, 분류, 권한)을 하나의 요청 흐름으로 조립한다.
- 정상 경로와 실패 경로(재전송, 변조, 잘못된 비밀값, 인증 없음)를 함께 실행해 확인한다.
- 조립할 때 새로 생기는 오류(인코딩, 트랜잭션 경계)를 찾는다.

선수 개념: 8.1절, 2.6·3.2·3.5·5.5·6.1절.

## 현장 상황

8.1절의 설계를 코드로 옮긴다. 부품은 각 장에서 따로 검증했지만, 조립하면 경계에서 새 문제가 생긴다. 이 절을 쓰는 동안 실제로 하나가 나왔다. 조회 예제에서 한국어 분류명을 URL에 그대로 넣자 `UnicodeEncodeError: 'ascii' codec can't encode characters`로 요청 자체가 실패했다. URL은 ASCII만 담을 수 있어 한국어는 퍼센트 인코딩해야 한다. 부품 테스트로는 보이지 않던, 조립 단계의 전형적인 오류다.

## 원리와 용어

요청 하나가 거치는 순서와 각 단계의 근거:

1. **서명·시각 확인**(2.6절): 원시 바이트로 HMAC을 계산해 `compare_digest`로 비교하고, 5분이 지난 요청은 거절한다. 파싱은 그다음이다.
2. **분류**(6.1절): 규칙이 정확히 한 분류를 가리킬 때만 규칙으로 정한다. 여러 분류에 걸치거나 단서가 없으면 "모델" 단계로 넘기고, 모델 결과도 허용 목록으로 검증한다. 통과하지 못하면 `검토필요`로 사람에게 보낸다. 이 예제의 "모델"은 결정적인 대체 함수이며, 실제로는 LLM 호출과 6.1절의 스키마 검증이 들어갈 자리다.
3. **가명화**(3.5절): 이메일을 HMAC 가명으로 바꾼다. 원문은 저장하지 않는다.
4. **저장**(2.5·3.2절): 이벤트 ID 기록과 문의 저장을 **한 트랜잭션**으로 한다. 이벤트 ID의 기본 키 제약이 재전송을 막는다. 중복이면 200으로 답해 보내는 쪽의 재전송을 멈춘다.
5. **조회**(2.2·5.5절): Bearer 토큰에서 테넌트를 얻고, 모든 질의에 `WHERE tenant = ?`를 강제한다. 매개변수의 값은 자리표시자로 넘긴다(3.1절).

서버는 공유 SQLite 연결을 쓰므로 쓰기를 잠금으로 직렬화했다. 학습용 `http.server` 구성이며, 운영에서는 검증된 웹 프레임워크와 서버형 DB를 쓰되 단계와 검증은 같다.

### 2) 처음부터 끝까지 실행

합성 문의 60건을 웹훅으로 보내고, 재전송·변조·잘못된 비밀값을 섞은 뒤, 두 고객사 토큰으로 조회한다.

::example capstone/demo.py

해설:

- 1) 60건이 모두 200으로 처리됐고 경로는 규칙 39, 모델 17, 사람 검토 4건이다. 사람 검토 4건은 "택배로 반품 보냈는데 환불 언제 돼요"(배송·환불 규칙에 동시에 걸림)와 "제 주문 내역이 하나도 안 보여요"(단서 없음) 같은 문의다. 틀리게 배정하지 않고 사람에게 넘겼다.
- 2) 같은 이벤트의 재전송은 200 "중복 이벤트(무시)"로, 변조와 다른 비밀값은 401로 막혔다.
- 3) 저장된 60건에 이메일 원문은 없고, 서로 다른 고객 25명이 가명 25개로 구분됐다.
- 4) 다라상사 토큰으로는 다라상사 문의만, 가나물류 토큰으로는 가나물류 40건만 보인다. 토큰이 없으면 401이다. 한국어 분류명은 `urlencode`로 인코딩했다.
- 5) 사람 검토 대기열의 건수는 운영 지표(5.1절)로 내보내야 할 값이다. 대기열이 쌓이는데 아무도 모르면 "안전한 실패"가 "조용한 방치"가 된다.

## 흔한 오류와 디버깅

- **URL의 비 ASCII 문자**: 쿼리 값은 `urllib.parse.urlencode`나 `quote`로 인코딩한다. 서버는 `parse_qs`로 디코딩한다.
- **트랜잭션 경계 실수**: 이벤트 ID만 먼저 커밋하고 문의 저장이 실패하면, 재전송이 "중복"으로 무시되어 그 문의를 영원히 잃는다. 둘을 한 트랜잭션에 넣은 이유다.
- **검증 전에 파싱**: 서명 확인 전에 `json.loads`를 하면 공격자가 보낸 큰 본문이나 이상한 입력을 먼저 처리하게 된다.
- **테넌트 조건 누락**: 새 조회 함수를 추가할 때 가장 빠뜨리기 쉽다. 5.5절의 권한 표 테스트를 이 시스템에도 둔다.
- **사람 검토 대기열 미관측**: 경보가 없으면 쌓인 문의가 방치된다(7.3절 런북의 대기열 경보).

## 이해 확인

::quiz
`ingest`에서 `events` 삽입과 `inquiries` 삽입을 별도 트랜잭션으로 나누고, 두 번째 삽입이 `CHECK` 제약 위반으로 실패했다. 보내는 쪽이 같은 이벤트를 재전송하면 어떻게 되는가?
::answer
첫 트랜잭션에서 이벤트 ID가 이미 커밋됐으므로 재전송은 `events`의 기본 키 위반으로 "중복 이벤트(무시)" 처리된다. 문의는 저장되지 않은 채 영원히 사라진다. 두 삽입을 한 트랜잭션으로 묶으면 실패 시 이벤트 기록도 롤백되어, 원인을 고친 뒤 재전송으로 복구할 수 있다.
::end

::quiz
분류 규칙에 "배송" 단어가 있으면 무조건 배송으로 정하도록 바꾸자는 제안이 나왔다. 데모의 사람 검토 4건 중 어떤 문의에 어떤 영향이 생기며, 수용 기준 중 무엇이 위험해지는가?
::answer
"택배로 반품 보냈는데 환불 언제 돼요"처럼 배송 단어와 환불 의도가 섞인 문의가 배송으로 잘못 자동 배정된다. 사람 검토가 줄어 자동 배정 비율은 오르지만 오배정이 생겨 "오배정 5% 이하"와 "환불 재현율 0.7 이상" 기준이 위험해진다. 여러 분류에 걸칠 때 사람에게 보내는 현재 규칙이 정밀도를 지키는 장치다(6.4절의 정밀도·재현율 트레이드오프).
::end
