## 학습 목표와 선수 개념

- 컨테이너 이미지가 해결하는 문제와 Dockerfile의 기본 지시어를 설명한다.
- CI 워크플로가 언제 무엇을 실행하는지 읽는다.
- 카나리 배포의 단계와 롤백 판단 기준을 코드로 표현한다.

선수 개념: 4.1–4.3절.

## 현장 상황

PoC는 FDE의 노트북에서 잘 돌았다. 고객사 서버에 옮기자 Python 버전이 달라 실행되지 않았고, 누군가 서버에서 직접 고친 파일 때문에 어떤 코드가 돌고 있는지 아무도 확신하지 못했다. 배포는 금요일 밤에 한꺼번에 했고, 문제가 생기자 이전 상태로 돌아갈 방법이 없었다. 공고들이 말하는 "첫 프로토타입부터 안정적 운영까지"(OpenAI FDE)는 이 간극을 메우는 일이다.

## 원리와 용어

### 컨테이너 이미지

**이미지**는 앱과 실행에 필요한 런타임·라이브러리를 묶은 읽기 전용 꾸러미이고, **컨테이너**는 이미지를 실행한 것이다. 같은 이미지는 노트북·CI·고객 서버에서 같은 환경으로 실행된다. Dockerfile의 주요 지시어:

- `FROM`: 기반 이미지. 버전을 고정한다(`python:3.13-slim`).
- `WORKDIR`, `COPY`: 작업 폴더와 파일 복사.
- `RUN`: 빌드 중 명령 실행(패키지 설치, 사용자 생성).
- `USER`: 실행 사용자. Docker 문서는 권한이 필요 없는 서비스라면 `USER`로 루트가 아닌 사용자로 바꾸라고 권한다.
- `CMD`: 컨테이너가 시작할 때 실행할 명령.

비밀값은 이미지에 넣지 않는다(4.3절). 이미지는 여러 곳에 복사되고 레이어를 열어 보면 내용이 드러난다.

### CI와 CD

- **CI(지속적 통합)**: 변경을 올릴 때마다 자동으로 빌드·테스트한다. 깨진 변경이 합쳐지기 전에 잡는다.
- **CD(지속적 전달·배포)**: 검사를 통과한 결과물을 배포 가능한 상태로 만들거나 자동으로 배포한다.
- GitHub Actions 워크플로는 `on`(언제), `jobs.<id>.runs-on`(어디서), `steps`(무엇을)로 구성된다. `uses`는 남이 만든 동작을, `run`은 셸 명령을 실행한다.
- CI는 저장소와 비밀값에 접근하므로 공격 대상이다. GitHub의 보안 지침은 (1) 서드파티 액션을 태그가 아니라 **전체 커밋 SHA로 고정**하고 (2) `GITHUB_TOKEN` 권한을 필요한 만큼만 주며 (3) PR 제목 같은 신뢰할 수 없는 입력을 `run` 명령에 직접 끼워 넣지 말라고 권한다. 아래 예제의 `permissions`와 SHA 고정이 그 적용이다.

### 단계적 배포와 롤백

**카나리 배포**는 새 버전에 트래픽 일부(5% → 25% → 50% → 100%)만 보내며 지표를 확인한다. 기준을 넘으면 즉시 이전 버전으로 되돌린다(**롤백**). 판단 기준은 배포 전에 정한다. 배포 중에 "이 정도면 괜찮겠지"라고 정하면 판단이 흐려진다. 롤백이 쉬우려면 이전 이미지가 남아 있어야 하고, DB 변경은 이전 버전과도 호환되게(예: 열 추가 먼저, 삭제는 나중 배포에서) 나눈다.

### 3) 카나리 배포 판단

실제 트래픽 대신 오류율을 흉내 내어, 단계별로 진행·롤백을 판단하는 규칙을 실행한다. 판단 규칙: 새 버전 오류율이 2%를 넘거나 기존보다 1%포인트 이상 높으면 롤백.

::example ch4/rollout.py

해설:

- `v2-good`은 단계마다 기존 버전과 오류율 차이가 작아 100%까지 진행했다.
- `v2-bad`는 첫 5% 단계에서 3.6%가 나와 바로 롤백됐다. 트래픽의 5%만 영향을 받았다. 한 번에 100%로 배포했다면 모든 사용자가 4% 오류를 겪었다.
- 5% 단계의 요청 수는 적어 오류율이 흔들린다. 실제로는 최소 요청 수와 관찰 시간을 함께 정한다.

## 흔한 오류와 디버깅

- **`latest` 태그**: 어제와 오늘 같은 태그가 다른 이미지를 가리켜 재현이 깨진다. 커밋 해시나 버전 태그를 쓴다(예제 CI의 `${{ github.sha }}`).
- **컨테이너가 127.0.0.1에 바인딩**: 컨테이너 안의 127.0.0.1은 밖에서 접근할 수 없다. `serve.py`처럼 0.0.0.0에 바인딩하고 포트를 연결한다.
- **CI에서만 실패**: 로컬과 CI의 버전·시간대·환경 변수 차이를 의심한다. CI 로그에 버전을 출력하는 단계를 둔다.
- **롤백할 수 없는 DB 변경**: 새 버전과 함께 열 이름을 바꾸면 롤백한 이전 버전이 동작하지 않는다. 확장 → 이전 → 축소 순으로 나누어 배포한다.

## 이해 확인

::quiz
Dockerfile에 `ENV API_TOKEN=abc123`을 넣었다. 무엇이 문제이고 어떻게 고치는가?
::answer
토큰이 이미지 레이어에 영구히 기록되어, 이미지를 받는 누구나 `docker inspect`나 레이어 확인으로 볼 수 있다. 이미지를 레지스트리에 올리면 유출 범위가 더 넓어진다. Dockerfile에서 지우고 토큰을 폐기·재발급한 뒤, 실행할 때 `docker run -e`나 오케스트레이터의 비밀 관리 기능으로 주입한다.
::end

::quiz
카나리 5% 단계에서 새 버전 오류율 0.9%, 기존 0.5%가 나왔다. 예제 규칙으로는 진행이다. 그런데 새 버전의 p99 응답 시간이 기존의 3배였다. 어떻게 판단해야 하는가?
::answer
오류율만 기준으로 삼으면 지연 문제를 놓친다. 지연(p95·p99)도 배포 기준에 넣어야 하며, 기준이 없었다면 진행을 멈추고 원인을 확인하는 것이 맞다. 5.1절의 황금 신호(지연·트래픽·오류·포화)를 배포 판단 지표로 쓰고, 기준은 배포 전에 정해 둔다.
::end
